# 几微 · 在自己的 iPhone 上用，以及上架 App Store

> 历史参考：记录当时的方案与环境，不代表现在仍存在同样问题。执行前核对当前代码和环境；当前开发入口见 [文档导航](../README.md)。

> 目标：**先在我自己的 iPhone 上真实用起来**，之后再看要不要上架。
>
> 这份文档把"能用"和"上架"分成两条完全不同的路 —— 它们的成本和风险差很多，
> 混在一起谈最容易走弯路。
>
> 所有外部结论都标了出处；标「不确定」的地方是真不确定，不要当结论用。

---

## 0. 结论先行

| 路线 | 需要什么 | 花多少钱 | 今天能做吗 | 适合 |
| --- | --- | --- | --- | --- |
| **A. PWA（加到主屏幕）** | 什么都不用装 | **¥0** | ✅ **今天就能** | **先用这个用一整个学期** |
| B. 原生 App，只给自己用 | Mac + Xcode，或云 Mac + TestFlight | ¥0（7 天要重装）或 ¥688/年 | ❌ 要先写原生代码 | 想要锁屏闹钟 |
| C. 上架 App Store | ¥688/年 + Mac + 过审 | ¥688/年 | ❌ | 想给同学用 / 想放简历 |
| D. TestFlight（不经审核的自用分发） | ¥688/年 + 云构建，**不需要 Mac** | ¥688/年 | ❌ | 想给自己和朋友装，又不想被审核 |

**三句话总结**：

1. **"我自己 iPhone 上能用"这个目标，今天就已经达成了** —— 而且不用上架、不用花钱、不用开发者账号。见第 1 节。
2. **上架最大的风险不是技术，是苹果的 4.2 条款**（"不要只是把网站包一层壳"）。
   几微现在直接封装提交，**大概率被拒**。要过审，必须先做出一个"浏览器标签页做不到"的功能 ——
   而那个功能已经在路线图里了（M5 的锁屏闹钟）。见第 3.2 节。
3. **中国的 App 备案有一条"不联网可豁免"的路，而几微天然符合** ——
   但前提是**永远不接第三方 SDK**。这一条同时满足了隐私、合规、成本三个目标。见第 3.3 节。

## 1. 路线 A：今天就能用（PWA，¥0）

**你现在不需要做任何开发，iPhone 上已经可以用了。**

### 步骤（30 秒）

1. iPhone 上用 **Safari** 打开 <https://arrsk.github.io/jiwei/>
   （**必须用 Safari**，微信内置浏览器、Chrome iOS 都不行）
2. 点底部中间的「**分享**」按钮（方框带向上箭头）
3. 往下滑，找到「**添加到主屏幕**」
4. 起个名字 → 「添加」

桌面上会多一个图标，点开是**全屏**的，没有地址栏，和装了个 App 一样。

### 为什么这条路比你想的好

很多人以为"网页加到桌面"是廉价替代方案，随时会被清数据。**在 iOS 上恰好相反**：

WebKit 官方博客明确说明，**加到主屏幕的 Web App 有自己的"使用天数"计数器，不属于 Safari**：

> "Web applications added to the home screen are not part of Safari and thus have their own counter of days of use… **We do not expect the first-party in such a web application to have its website data deleted.**"
> —— [WebKit 官方博客（ITP 7 天上限的出处）](https://webkit.org/blog/10218/full-third-party-cookie-blocking-and-more/)

也就是说，Safari 标签页里那套"7 天不用就清数据"的规则，**对加到桌面的 Web App 不适用**。
关键前提是 manifest 里 `display` 必须是 `standalone` —— 几微已经是了（构建冒烟检查里有一项专门守这个）。

### 这条路的局限（必须知道）

| 局限 | 说明 |
| --- | --- |
| **没有锁屏闹钟** | 这是浏览器的硬限制，见 [ALARM-STUDY.md](ALARM-STUDY.md)。想做闹钟必须走路线 B/C |
| App Store 里搜不到 | 不能分享给不熟的人 |
| iOS 上有个 IndexedDB 的真风险 | 见第 2.2 节，**这是打包成 App 之前必须先解决的** |
| 没有桌面小组件 | 想看"下一节课"还是得点开 |

### 建议

**先用这条路用一整个学期。** 理由：

- 零成本，今天就能开始；
- 你会真实地知道"缺的到底是闹钟，还是小组件，还是别的" —— 这比现在猜准得多；
- 如果你用下来发现"其实够用"，那就省下了 ¥688/年 和一大堆审核麻烦。

> ⚠️ **照旧每学期导出一次备份**（齿轮 → 备份与恢复）。不管走哪条路，这条都成立。

## 2. 路线 B：封装成真原生 App（只给自己用）

### 2.1 技术方案：Capacitor

项目在 [`ARCHITECTURE.md`](../ARCHITECTURE.md) 与 ADR-005 / ADR-006 里已经定了：
用 **Capacitor** 把 `apps/web` 的构建产物包进原生壳，**不重写 UI**。
这是唯一能"网页和原生共用一套代码"的路径。

### 2.2 ⚠️ 打包之前必须先做的一件事：换掉存储

**这是本文最重要的一条技术提醒。**

Capacitor 官方文档对 WebView 存储的定性是：

> "Local Storage… **must be considered transient**… the OS will reclaim local storage from Web Views if a device is running low on space. **The same can be said for IndexedDB at least on iOS**"
> —— [Capacitor 官方 Storage 指南](https://capacitorjs.com/docs/guides/storage)

更要命的是 WebKit 的 #277615：**Capacitor 应用在 iOS 上，IndexedDB 连接会自发断开且无法恢复**
（app 后台挂几小时后回前台就触发，用户必须强杀 App）。Dexie 作者本人在那个线程里说：

> "**Dexie.js is not able to workaround this issue.** … we've also tried whether reopening the database helps in this case but unfortunately it does not."
> —— [WebKit Bugzilla #277615](https://bugs.webkit.org/show_bug.cgi?id=277615)

**这对几微是致命的**：课表是用户手输的、丢了就没了的东西。

好消息是 WebKit 工程师在 2026-03 回复说连接无法重连的子问题**已在 #309386 修复，预计随版本发布**。
但这是"预计"，不是"已上线"。

**建议**：打包成原生 App **之前**，把存储从 IndexedDB 换成 SQLite。
这不需要改业务代码 —— 项目当初就是为这一刻设计的（ADR-003 / ADR-007：仓储接口隔离，
**换引擎只换一个入参**）：

```
packages/data/src/engines/dexie/   →   新增 packages/data/src/engines/sqlite/
@capacitor-community/sqlite
```

换完之后，`features/*` 一行都不用改。这正是前面所有架构克制的回报。

> 顺带一提：这个问题在 **PWA** 上风险小一些（iOS 对主屏幕 Web App 的处理不同），
> 但也别赌 —— 备份照做。

### 2.3 需要一台 Mac（这是最大的现实摩擦）

**Xcode 只能在 macOS 上运行**，这是硬门槛。三条子路线：

| 方式 | 需要 | 装到自己手机的代价 | 适合 |
| --- | --- | --- | --- |
| **免费 Apple ID + Xcode** | 一台 Mac（借/租） | 证书 **7 天过期**，每 7 天要连一次 Xcode 重装 | 只想试试效果 |
| **付费开发者账号 + Xcode** | Mac + ¥688/年 | 证书 1 年；可给别人装 | 长期自用 |
| **付费账号 + TestFlight** | ¥688/年，**不需要 Mac**（云构建） | 用 TestFlight App 装，一次 90 天，点一下就续 | **没有 Mac 的人** |

就你的情况（Windows 电脑），**第三条路是最实际的**：见 2.4。

### 2.4 没有 Mac 怎么办

| 方案 | 说明 | 成本 |
| --- | --- | --- |
| **GitHub Actions 的 macOS 构建机** | 仓库是**公开**的 → macOS runner **免费**。可以在 CI 里 `npx cap sync ios` 并归档 | 免费 |
| **Codemagic / Xcode Cloud** | 专门的 iOS 云构建服务，有免费额度 | 免费额度 / 按月 |
| 租云 Mac（MacinCloud 等） | 有完整桌面，可以用 Xcode | 约 ¥200+/月 |
| 借朋友的 Mac | 最快，且能直接帮你解决签名报错 | 人情 |

**关键点**：即使云构建能产出安装包，**"装到你自己 iPhone 上"这一步**仍然需要签名身份：

- 免费 Apple ID 的签名 **只在 Xcode 里有效**（要连一台 Mac）；
- 付费账号可以用 **TestFlight**，完全不需要 Mac。

**所以结论是**：想在没有 Mac 的情况下把原生 App 装进自己 iPhone，
**最省事的组合是「¥688/年 开发者账号 + GitHub Actions 云构建 + TestFlight」**。
免费 Apple ID 那条路，绕不开一台 Mac。

## 3. 路线 C：上架 App Store

### 3.1 前置条件清单

| 项目 | 要求 | 几微的现状 |
| --- | --- | --- |
| 开发者账号 | Apple Developer Program，**约 ¥688/年**（$99，以注册页为准） | 需购买 |
| 构建环境 | macOS + Xcode（或云 Mac） | 需解决 |
| **隐私政策 URL** | 必须能公开访问 | ✅ 可直接挂 GitHub Pages，**不需要备案** |
| **支持 URL** | 必须能公开访问 | ✅ 同上 |
| 应用图标 | 1024×1024 | 需制作 |
| 截图 | 至少 6.7" 与 6.5"，各 3~10 张 | 需制作 |
| App Privacy 问卷 | 如实填写 | ✅ 几微可填"**不收集任何数据**"，这是优势 |
| 年龄分级 | 4+ | 简单 |
| 中国大陆分发 | **ICP 备案号，或申请豁免** | ✅ 符合豁免条件，见 3.3 |

> 实用信息：多位开发者实测，**隐私政策和支持页挂在 GitHub Pages 上就行**，
> 苹果不要求它们备案。这一点几微已经具备（同一套 Pages）。

### 3.2 ⚠️ 最大的审核风险：4.2 Minimum Functionality

这是"网页套壳"类应用被拒的头号原因，来自苹果审核指南 4.2：

> Apps should include features, content, and UI that **elevate it beyond a repackaged website**.

行业侧的判据说得更直白：

> "**如果同样的内容在 Safari 里打开，功能完全没有损失，那 App Review 就没有理由把它当成一个独立产品。**"
> —— [AcceptMyApp: Wrapping a web app for iOS](https://acceptmy.app/guides/web-app-to-ios-app-store-requirements)

**能过审的壳 vs 被拒的壳**，分界线是这几个：

| 通过的做法 | 几微现状 |
| --- | --- |
| 原生通知，且**绑定真实事件**（不是空泛的"开启通知"） | ❌ 未做（M5） |
| **真实的离线能力**（不是断网白屏/转圈） | ✅ 已有（Service Worker + 本地数据） |
| **至少一个浏览器标签页做不到的原生能力**：桌面小组件、Face ID、分享扩展、后台同步 | ❌ 未做 |
| 不出现浏览器痕迹（地址栏、跳出到 Safari 的链接） | ✅ 已经是 standalone |

**所以我的判断是：现在直接封装提交，大概率被 4.2 拒。**

而且要提醒一句：**换个图标、改个界面名字再提交，第二次几乎不可能过** ——
苹果要的是**真加原生功能**，不是化妆。

### 3.3 中国大陆分发：ICP 备案，以及"不联网可豁免"

中国大陆区上架需要有 ICP 备案号。但有一条豁免路径，**几微天然符合**：

> "如果你的 App **不联网**，或者虽然联网，但**只连接 Apple 的服务器使用 iOS 系统服务**（如完成 App 内购买），
> 是可以向苹果申请豁免 ICP 备案的。否则都需要备案，不能豁免。"
> —— [V2EX：教大家如何申请豁免中国大陆地区 App Store ICP 备案](https://global.v2ex.co/t/1232582)（作者自述为实测）

**几微是纯本地应用，一个服务器都没有，也不上传任何数据 —— 完全符合豁免条件。**

#### 申请豁免的步骤（按上面那条记录）

1. 打开 <https://developer.apple.com/cn/>，拉到最底下「**联系我们**」
2. 选「有新的问题」→「查看主题」
3. 选「**分发**」→「有关分发的其它疑问」
4. 填表。注意「应用的 Apple ID」指的是 **App Store Connect 后台里这个 App 的 Apple ID**，不是你的 Apple 账户 ID
5. 「重现步骤」写"无"；在信息栏里说明：本应用无需联网，联网权限（如果有）仅用于 Apple 内购，申请豁免 ICP 备案
6. 等苹果邮件。一般**第二天**会联系你补一份声明，回复后通常就能豁免

另一种做法（有人成功，但依赖审核员）：**直接在审核备注里写明"本应用不需要联网，
依据相关法律法规不需要备案"，并附上工信部法规链接**。

#### ⚠️ 一个必须守住的纪律

同一个帖子里有个反面案例：一位开发者最初没备案也过审了，后来**加了 Firebase Crashlytics**，
**App 就被从中国区下架了**。

> 注释：接入第三方 SDK 意味着"应用会连接非 Apple 的服务器"，
> 豁免的前提（不联网 / 只连 Apple）就不再成立。

这条纪律和 [产品与商业化研究.md](产品与商业化研究.md#商业研究) 第 4 节里"**不接入任何第三方统计 SDK**"是同一个决定，
也和 ADR-002（不做服务器）一致。**一个决定同时满足隐私、合规、成本三件事** ——
这是这个项目架构上最划算的一笔。

### 3.4 其他合规

| 事项 | 要求 | 几微 |
| --- | --- | --- |
| 账号删除 | 若应用支持注册，必须提供应用内删除账号 | ✅ 无账号，不适用 |
| 内购 | 收费必须走 IAP，不能外链支付 | 现阶段不收费，不适用 |
| 权限用途说明 | 每个权限要有中文说明 | 几微几乎不要权限，这是优势 |
| **不索要教务账号密码** | 见第 3.6 节 | ✅ 明确不做 |

### 3.5 提交步骤（从零到上架）

```
① 买开发者账号（¥688/年，个人身份即可，iOS 不需要软著）
        ↓  审核通常 1~2 天
② 做原生增强（见 3.2）：本地通知闹钟 + 桌面小组件
        ↓
③ 迁存储到 SQLite（见 2.2）—— 这一步不能省
        ↓
④ npx cap add ios && npx cap sync ios   （需要 Mac 或云 Mac）
        ↓
⑤ 准备素材：1024 图标、两套截图、隐私政策页、支持页
        ↓
⑥ 隐私政策 / 支持页发到 GitHub Pages（免费，无需备案）
        ↓
⑦ Xcode Archive → 上传 App Store Connect（或云构建上传）
        ↓
⑧ 填 App 信息 + App Privacy 问卷（勾"不收集数据"）+ 申请 ICP 豁免
        ↓
⑨ 提交审核 → 通常 1~3 天出结果
        ↓
⑩ 被拒就照 3.2 补原生功能，不要只改表面
```

### 3.6 一条特别适用于本项目的建议

几微决定"**不做教务抓取、不索要教务账号密码**"，这在审核上反而是**加分项**：
不需要解释"我们为什么要用户提供学校账号"，也就没有那条最容易被拒的合规风险
（学校已公开声明这类行为涉嫌违法，见 [产品与商业化研究.md](产品与商业化研究.md#商业研究) 第 1.4 节）。

## 4. 建议的执行顺序

| 阶段 | 做什么 | 为什么现在做这个 |
| --- | --- | --- |
| **阶段 1（今天）** | **PWA 加到主屏幕，用起来** | 零成本，立刻满足"自己 iPhone 上能用" |
| **阶段 2** | M2（安装引导、字号）+ M3（iCal 订阅、兼容竞品导入） | 提升真实使用体验 |
| **阶段 3** | 迁存储到 SQLite（ADR-003 的触发条件已到） | 为原生打包扫清最大的数据风险 |
| **阶段 4** | M5：Capacitor + **本地通知闹钟** + **桌面小组件** | 这才是"浏览器做不到"的东西，也是过 4.2 的门票 |
| **阶段 5** | TestFlight 自用 → 稳定后再考虑提交审核 | 先自己和朋友用，别一上来就面对审核 |

### 关于 iCal 订阅的一个补充

[产品与商业化研究.md](产品与商业化研究.md#商业研究) 建议把 **iCal 订阅**提到最前，作为"没有闹钟"的低成本替代。
这个建议在**原生化之后可以升级**：

| 场景 | 做法 | 体验 |
| --- | --- | --- |
| 现在（PWA） | 生成 `.ics` 文件 / 订阅链接，用户手动加到系统日历 | 借用系统闹钟，但要多几步、且不会自动更新 |
| 原生化之后 | 用 **EventKit** 直接把课表写进系统日历 | 一步到位，且能双向同步 —— 这是又一个"浏览器做不到"的原生能力 |

**所以 iCal 订阅不是白做**：它是原生 EventKit 方案的接口设计预演，
两者共用同一套"把 Occurrence 映射成日历事件"的逻辑。

## 5. 诚实的风险提醒

| 风险 | 严重度 | 说明 |
| --- | --- | --- |
| **没有 Mac** | 高 | 最大的现实摩擦。短期解法是付费账号 + 云构建 + TestFlight（不需要 Mac） |
| **iOS IndexedDB 数据丢失** | 高 | 打包前必须迁 SQLite。这是"用户手输的东西丢了就没了"的问题，不能赌 |
| **4.2 被拒** | 高 | 现在封装就提交，大概率被拒。必须真加原生功能 |
| **¥688/年** | 中 | 每年都要交，不上架也要交（TestFlight 也要）。**先用 PWA 半年再决定** |
| ICP 豁免被后续审核推翻 | 中 | 首个版本没备案可能放行，但后续有被下架的风险（已有真实案例）。**不要接第三方 SDK** |
| 你只有一个开发者账号 | 低 | 个人账号上架的应用会显示你的**真实姓名**（可改为公司名，需另行申请） |

## 6. 现在就可以做的三件事

1. **今天**：用 Safari 打开 <https://arrsk.github.io/jiwei/> → 添加到主屏幕，开始用它上课。
2. **这学期**：每次课表有变动就用一下调课/停课功能，期末导出一次备份。**观察自己到底缺什么。**
3. **学期末**：如果发现"最缺的是锁屏闹钟"，那就走阶段 3→4；如果发现"其实够用"，
   就把开发精力放回 M3（数据进出）而不是原生包 —— **省下 ¥688/年 和几个月的审核折腾**。
