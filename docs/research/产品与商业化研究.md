# 几微 · 产品分析：需求、竞品、变现与迭代方向

> 这份文档回答四个问题：**大学生到底有多需要它 / 竞品强在哪弱在哪 / 怎么变现 /
> 怎么做不冒犯用户的数据调研**，并据此给出迭代优先级的调整建议。
>
> 所有外部论据都在文中标注了出处，最后一节列了链接。
> **文中标了「估计」的数字是我的推算，不是实测数据** —— 请当作假设，用第五节的方法去验证。

## 0. 结论先行

| 问题 | 结论 |
| --- | --- |
| 需求程度 | **真实，但被高估**。它是"高价值、低频次、易替代"的工具，不是"刚需高频"。真正的窗口期只有开学前后 2~3 周 |
| 竞品优势 | 几微的优势**不在功能，而在"反面"**：不注册、不广告、不臃肿、不碰教务账号、离线可用。而竞品的差评恰好全集中在这五条上 |
| 变现 | **靠课表本身几乎不可能独立变现**。学生付费意愿低、课表打开频次低、广告会直接摧毁唯一优势。最现实的三条路是：班级/社团版、iCal+同步的买断制、开源赞助；最现实的目标其实是"自用 + 作品集" |
| 数据调研 | 分四层，**从零隐私成本的方法开始**（竞品差评挖掘 > 深访 > 主动招募问卷 > 可选的自托管统计）。绝不接入任何第三方统计 SDK |
| 迭代方向 | **把 iCal 订阅提到最前面**（用最低成本解决"没闹钟"这个最大短板），紧接着做**兼容竞品导出文件的导入**（合法地绕开"不做教务抓取"的限制）。日程/任务/笔记要等留存验证之后再动 |

**一句话**：这个项目的护城河是"**克制**"，而克制本身不产生收入 —— 所以要靠"不做坏事"换来信任，再用信任换一个很小的付费点，而不是反过来。

## 1. 需求程度分析

### 1.1 先破除一个幻觉：课表 App 是"刚需高频"吗

一篇在校园创业圈流传很广的分析把这件事说得很直白：

> "课表类App真的是'刚需高频'吗？这有点像假期我们背回家的书：不背回家觉得对不起时间，背回去了其实也不会用得到。"
> —— [《校园用户争夺战（一）：课表类App正走在下坡路上》](https://www.downol.com/dianlaoruanjian-28345)

它把学生分成三类：

| 类型 | 为什么不用课表 App |
| --- | --- |
| 学霸 | 课程早就记住了，或者直接看教务系统 |
| 学渣 | 反正也不去上课 |
| "聪明"的学生 | 开学时用一次生成课表，**截图存相册**，之后再也不打开 |

这个判断有它的道理，而且指出了一个残酷事实：**课表 App 最大的竞品不是另一个 App，是"截图 + 手机相册"。**

### 1.2 但有三个新变量，让今天的需求比十年前更真实

十年前的判断不完全适用于现在：

1. **选课制 + 学分制普及** → 同一个班每个人的课表都不一样，"我的课表"成了个人信息，不能再靠同学之间问。
2. **多校区 / 走班 / 教室分散** → "下一节课在哪栋楼"变成每天要问的问题。
3. **系统日历对"教学周"支持极差** → 单双周、第 3 周开始、第 9 周停课，这些**系统日历表达不了**。这是课表 App 目前唯一不可替代的技术缝隙。

所以我给需求强度的判断是：

| 维度 | 评价 | 说明 |
| --- | --- | --- |
| 需求真实性 | ★★★★☆ | 确实存在，学校自己都承认（见 1.4） |
| 使用频次 | ★★☆☆☆ | 开学 2~3 周很高，之后降到每天 0~1 次，很多人干脆不看 |
| 需求强度 | ★★★☆☆ | 漏看一节课的代价很高（点名、迟到），所以**价值**不低 |
| 可替代性 | ★★★★★ | 截图、系统日历、教务 App、同学群里问、班委发的 Excel |
| 付费意愿 | ★☆☆☆☆ | 见第三节的实测调查 |

**定位结论**：课表是「**高价值、低频次、易替代**」的工具。
它不适合作为一个独立的商业产品，但**非常适合作为"大学生活 App"的入口** ——
因为它是唯一一个"全校每个人都必须关心、且信息天然结构化"的东西。

### 1.3 需求的真实证据：从竞品差评里挖

判断需求最便宜的方法不是发问卷，而是看**已经在用同类产品的人骂什么**。
这是零隐私成本、零打扰的一手数据。下面是从应用汇上「超级课程表」真实用户评论里摘的原话：

| 用户原话 | 暴露出的真实需求 / 痛点 |
| --- | --- |
| "就用一个课程表，你要手机号码注册干什么？还要定位干什么？" | **不要为看课表付隐私代价** |
| "广告太多了……" | 广告容忍度极低 |
| "广告直接出现在中间正上方，直接不能切换星期（不然一点就转去其他应用）" | **广告挡住了核心操作**，这是最致命的一种伤害 |
| "本来用就只要一个课表，做这么多与课表无关的拓展服务实在离谱" | **功能臃肿 = 负价值** |
| "导入课表是做出来搞笑的吗，登了半个小时都没登上教务系统，每次都是密码错误，我都改三次密码了" | 一键导入**不可靠**，且用户在反复输密码 |
| "教务系统导入都不行了，还好用个篮子" | 依赖学校系统 = **随时失效** |
| "害我好几次迟到了" | 可靠性是底线，坏一次就流失 |
| "学校不是都有自制的软件么" | 校方自建是强力替代 |
| "如果用腻了超级课程表，那就用 wake up" | **迁移成本极低**，没有忠诚度 |
| "越来越垃圾，还不停有骗子发诈骗信息" | 校园社交/开放互动带来安全风险 |

这张表基本就是几微的产品需求文档。**竞品把自己最弱的五条全暴露了：隐私、广告、臃肿、教务依赖、可靠性。**

### 1.4 学校自己的态度：需求的另一面证据

长沙理工大学教务处在 2026 年 3 月发的声明，间接证明了需求的存在，也划出了一条红线：

> "对任何以'便捷查课表'、'快速算绩点'、'学业分析'等名义索要教务账号密码的校外服务，均应保持高度警惕，坚决拒绝提供。"
> "任何未经我校明确授权，通过任何技术手段（包括但不限于诱导学生分享账号密码、自动化脚本抓取、系统漏洞侵入等方式）非法获取、使用我校教务管理系统内数据的行为，均涉嫌违反《网络安全法》《数据安全法》《个人信息保护法》……我校保留对相关侵权主体依法追究其法律责任的一切权利。"
> —— [长沙理工大学教务处声明](https://www.csust.edu.cn/jwc/info/1101/7727.htm)

三个信息点：

1. 学校承认学生有"**便捷查课表**"的需求（否则不会有第三方去做）；
2. 学校**从未授权**任何第三方接入 —— 所以"官方合作"的宣传都是假的；
3. 这条路现在是**法律风险**，不只是技术风险。

> **这直接支持了项目 ADR-001 的决定：不做教务抓取。** 但它也带来一个必须正视的代价，
> 见 2.4。

### 1.5 需求的天花板

| 压制需求的因素 | 影响 |
| --- | --- |
| 教务抓取被学校封禁、且违法风险上升 | "一键导入"这条最能促成转化的路越来越窄 |
| 校方自建（今日校园 / 企业微信 / 教务处 App） | 学校自己把需求吃掉了 |
| iOS/Android 系统日历 + 手动录一次 | 对"只想知道几点在哪"的人够用 |
| 学生只在开学用一次 | 留存天然很差 |

**所以需求判断的落点**：不要指望"课表"本身撑起一个产品。
它只能作为**入口**，而能不能留住人，取决于入口之外那一步 —— 这正是第五节要回答的。

## 2. 竞品分析

### 2.1 竞品地图

| 竞品 | 类型 | 强项 | 弱点 |
| --- | --- | --- | --- |
| **超级课程表** | 安卓为主的老牌头部 | 教务一键导入覆盖学校多；品牌认知度高；历史上注册用户量达千万级（**2015 年前后数据：2000 万注册 / 日均 200 万**，见出处一） | 强制手机号注册、要定位；广告侵入核心操作；功能臃肿且有社交诈骗风险；被用户做成"去广告模块" |
| **课程格子** | 老牌第二 | 曾是"课表 + 轻社交"的开创者；1700 万注册 / 150 万日活（同期数据） | 转型社区/电商失败，社区活跃度崩塌；**已基本退出主流** |
| **WakeUp 课程表** | 当前 iOS 主流 | 界面干净、纯本地、口碑好；是用户在超级课程表之外的首选替代 | 生态相对单一；无跨端同步 |
| **极简课程表 / 星课程表** 等 | 新入局者 | 主打"极简""Watch 联动" | 功能面窄，多为个人/小团队作品 |
| **系统日历（iOS/Android/鸿蒙）** | 系统自带 | 零安装、系统级提醒、锁屏可见 | **表达不了单双周/教学周**；录入麻烦 |
| **今日校园 / 企业微信 / 教务处 App** | 校方官方 | 数据最准、学校背书 | 体验普遍差，只解决"看"，不解决"用" |
| **滴答清单 / Notion / 飞书** | 通用效率工具 | 能力强、跨端同步好 | 要自己建模，课表场景没有开箱即用 |
| **截图 + 手机相册** | **真正的最大竞品** | 零成本、零学习、够用 | 不能搜、不能改、不能提醒 |

### 2.2 竞品的护城河有多深？

要诚实：**这些竞品几乎没有护城河，只有规模。**

- 用户迁移成本极低（差评里直接说"用腻了就换 wake up"）；
- 数据是用户自己录的，随时可带走；
- 功能不存在技术壁垒（几微用几周就做出了核心功能）。

所以对竞品来说，**唯一能留住用户的是"习惯"和"学校覆盖数"**，
而这两样对新入场者都是坏消息，除非走一条完全不同的价值主张 —— 那就是几微现在这条路。

### 2.3 几微的真实优势（逐条判断可持续性）

| 优势 | 用户价值 | 可持续性 |
| --- | --- | --- |
| **零注册、零账号** | 直接命中"你要我手机号干什么"的怨气 | 🟢 高 —— 有服务器才能同步，所以竞争对手**很难**为了体验而放弃账号体系 |
| **零广告、无开屏** | 直接命中"广告挡住切换星期" | 🟢 高 —— 广告是头部竞品的主要收入，它们退不回来 |
| **不碰教务账号密码** | 规避盗号、诈骗、法律风险 | 🟢 高 —— 学校已公开定性为非法，这条会越来越值钱 |
| **离线完整可用** | 地铁、教学楼弱网照样看 | 🟡 中 —— 竞品也能做，但它们的架构偏云端 |
| **数据只在本机** | 隐私焦虑的解药（25% 的用户因隐私拒付/拒用，见 3.1） | 🟢 高 —— 这是架构级选择，改起来代价极大 |
| **一套代码覆盖电脑/手机/桌面** | iOS 和电脑用户有得用（竞品几乎都是安卓优先） | 🟡 中 |
| **东西少、上手快** | 反对臃肿 | 🟡 中 —— "少"既是优点也是天花板 |

**共同点**：这些优势全部来自"**不做某件事**"。
这类优势的特点是——**极难被抄袭，但也极难变现**，因为用户不会为"你没做坏事"付费，
他们只会因此**留下来**。

### 2.4 几微最大的劣势（必须正视）

| 劣势 | 后果 |
| --- | --- |
| **不能一键导入教务** | 用户第一次打开要**手动录 8~12 门课**。估计 5~10 分钟。竞品是 10 秒。**这是最大的一处流失点，可能直接损失大部分潜在用户** |
| 没有锁屏闹钟 | 已经在 README 里如实说明，但这是很多人的第一需求 |
| 没有 iOS 原生包（目前只是 PWA） | App Store 搜不到，传播受限；iOS 存储还有被回收的风险 |
| 手机与电脑数据不通 | 换设备要手动导出导入 |
| 单人项目、无运营 | 没有推广渠道，只能靠口碑 |

> **诚实的结论**：几微现在做的是**"给愿意忍耐手动录课的那部分人"**的产品。
> 这部分人不多，但他们的需求（干净、隐私、可靠）被现有产品**系统性地亏待**了。

### 2.5 一个可以绕过最大劣势的办法（重要）

"不能抓教务"和"必须手动录课"之间，其实有一条**合法的中间路**：

> **兼容竞品的导出文件。**
> 让用户先在 WakeUp / 超级课程表里用它们的"一键导入"拿到课表，
> 再从那里**导出**成文件，然后在几微里**导入**这个文件。

这样：

- 用户拿到"一键"的便利（在别的 App 里完成）；
- 几微**从头到尾没碰过教务账号密码**，法律与道德风险为零；
- 代价只是多两步操作，比手动录 10 门课好得多。

这条路不需要任何授权，也不违反学校声明（声明禁止的是"索要教务账号密码"和"非法侵入"）。
**建议把它作为 M3 的最高优先级之一**（详见 5.1）。

## 3. 变现手段

### 3.1 先看清现实：大学生愿意为什么付费

封面新闻 2026 年 6 月调查了 20 位成都大学生，问"AI 工具每月 38 元你付不付"：

> 45% 回复免费版够用，没必要付费；30% 认为**考试周、论文季、找工作阶段**愿意付费尝试；20% 处于观望；5% 调侃穷但想用。
> 总结：约**七成不会立即付费**，真正愿意长期订阅的大概**三成**。
> 另外：40% 表示**"付费之后还限制次数"最容易引发不满**；25% 会**因隐私问题被劝退**。
> —— [封面新闻调查](https://cbgc.scol.com.cn/news/7701457)

（样本只有 20 人、单个城市、且问的是 AI 工具不是课表，只能当**方向性参考**。）

对课表 App 的推论：

| 结论 | 对产品的要求 |
| --- | --- |
| 订阅制很难 | 不要做"每月 X 元"，学生会算得很清楚 |
| "场景性付费"有空间 | 付费点要绑定**具体时刻**（开学导入、考试周、毕业前） |
| **限次数是最招骂的** | 要做就做**买断/一次性**，不要给功能加额度 |
| **隐私是付费意愿的杀手** | 一旦要账号、要上传，连免费用户都会跑 |

### 3.2 变现方案清单（按可行性排序）

| # | 方案 | 天花板 | 风险 | 评价 |
| --- | --- | --- | --- | --- |
| 1 | **不变现**（自用 + 作品集） | 0 元 | 无 | **最现实**。这个项目对求职的价值远大于直接收入 |
| 2 | **开源赞助**（爱发电 / GitHub Sponsors） | 低（估计每月几十~几百元） | 无 | 与"不开广告"的价值主张完全一致，可以做 |
| 3 | **买断制高级版**（一次性 ¥18~38） | 低 | 低 | 必须绑定"真需要服务器"的能力（见 3.3） |
| 4 | **班级 / 社团版** | 中 | 低 | **最值得试**：付钱的是班委/辅导员，用的是全班 |
| 5 | 校园流量导流（CPA / 信息流广告） | 中 | **高** | 与核心价值直接冲突，**建议永久放弃** |
| 6 | 数据变现 | 低 | **法律+道德红线** | **明确不做**，也不要有任何中间态 |

### 3.3 如果要做付费，唯一说得通的产品形态

付费点必须**不是**"解锁本来就该有的功能"，而是"**需要成本、因此必须收费**"的能力：

| 付费能力 | 为什么可以收费 | 对应里程碑 |
| --- | --- | --- |
| **多设备同步** | 需要一台服务器，成本真实存在 | M8 |
| **iCal 订阅链接（长期可用）** | 需要服务端持续生成订阅源 | M3 |
| **班级/社团共享课表** | 需要服务端存储与分享 | 新方向 |
| 主题、字号、图标 | 开发成本一次性 | M2 —— **不建议收费**，容易招骂 |

**不要卖**：导出备份、离线使用、深色模式、基本编辑功能。
这些一旦收费，就直接背叛了现在所有"干净"的宣传口径。

### 3.4 算一笔账（估计，用于校准预期）

假设做到 1000 个真实活跃用户：

| 方案 | 假设 | 收入 |
| --- | --- | --- |
| 开源赞助 | 1% 的人赞助 ¥20 | ≈ ¥200（一次性） |
| 买断制 ¥25 | 3% 转化 | ≈ ¥750（一次性） |
| 班级版 ¥199/学期 | 覆盖 10 个班 | ≈ ¥2,000/学期 |
| 开屏广告 | 1 万次展示 | 几元~几十元 |

结论：**除"班级版"之外，都无法覆盖维护成本**。
所以对这个项目，"变现"的现实意义是：**验证能不能被愿意付费的人接受**，
而不是真的靠它生活。

### 3.5 明确画红线的三件事

写在这里，是为了将来（包括我自己）不自我说服：

1. **不卖数据、不做用户画像、不接第三方统计 SDK。**
2. **不做开屏广告、不做信息流广告、不在核心操作路径上放任何商业内容。**
3. **永不索要教务系统账号密码**，也不做任何形式的自动化抓取。

这三条是产品的立身之本。破任何一条，几微就变成了它当初要反对的那个东西。

## 4. 可接受的数据调研方案

### 4.1 原则：数据承诺本身就是产品的一部分

README 和使用说明里已经写了：**"不上传、不注册、数据只在你设备上"**。
这句话是卖点，不是修辞。所以：

> **任何埋点都是对用户的例外，必须满足三个条件：用户知情、默认关闭、拒绝后功能不减。**

违反这条，损失的不是合规性，是**唯一的产品优势**。

### 4.2 四层方案（从零成本到有成本，按性价比排序）

#### 第 1 层：零隐私成本（**现在就做，性价比最高**）

| 方法 | 怎么做 | 能回答什么 |
| --- | --- | --- |
| **竞品差评系统性挖掘** | 抓取 App Store / 应用汇 / 酷安 / 贴吧上竞品的**全部差评**，建 CSV：`日期 / 竞品 / 星级 / 原文 / 痛点标签 / 场景`。目标 200 条起，按标签聚合 | 真实痛点排序、功能优先级、措辞素材 |
| **学校官方文件** | 各校教务处通知、学期制度、选课规则变化 | 需求的结构性变化 |
| **GitHub Issues / Discussions** | 让用户主动提，公开透明 | 愿意发声的那部分用户 |
| **搜索引擎 / 社交平台话题** | "课程表 App 推荐""早八""教务系统崩了" | 场景与情绪 |

> 这一层**不接触任何用户数据**，拿到的却是最真实的需求，应该占调研工作量的 60%。

#### 第 2 层：主动招募 + 知情同意

| 方法 | 规模 | 要点 |
| --- | --- | --- |
| **半结构化深访** | 10~20 人 | 一次 30 分钟，问"上一次打开课表是什么时候、为什么"，**不要问"你想要什么功能"** |
| **在线问卷** | 100~300 份 | 腾讯问卷/问卷星；**不收集姓名、学号、学校全称**；只问行为与场景 |
| 同学群 / 校园大使 | 1~3 个学校 | 找愿意反馈的人，避免自嗨 |

**知情同意怎么写**（最小可用版，放在问卷和访谈开头）：

> 这是一个人开发的学习项目，我想知道课表 App 到底哪里不好用。
> 这份问卷**不收集**你的姓名、学号、手机号，也没有任何登录。
> 结果只用来排功能优先级，不会对外发布原始数据，30 天后删除。
> 你可以随时停止，不填任何一题。

#### 第 3 层：可选的、默认关闭的产品内统计（**建议 M2/M3 阶段不做**）

如果将来真的有 100+ 真实用户、且第 1、2 层回答不了问题时，才可以考虑：

| 要求 | 具体做法 |
| --- | --- |
| 自托管 | 用 [Umami](https://umami.is/) 或 Plausible 的**自托管**版本，**不接入任何第三方 SaaS** |
| 只记事件名 + 计数 | 例如"添加课程""切到日视图"，**不记设备 ID、不记时间戳序列、不记课程内容** |
| 默认关闭 | 首次启动用大白话告知 + 一键关闭；关掉后功能完全一样 |
| 不做画像 | 不做分群、不做漏斗归因、不做 A/B 实验 |
| 可查可删 | 提供"我贡献了什么数据"的查看页 |

**技术上的一条硬规则**：不要为了省事接入第三方统计 SDK —— SDK 本身就是数据外流通道，
而且会污染"无服务器"的架构叙事。

#### 第 4 层：明确不做

- ❌ 设备指纹 / 跨站标识
- ❌ 行为序列、点击热图、录屏回放（FullStory 类）
- ❌ 任何形式的数据出售、共享、用于训练模型
- ❌ 在用户不知情的情况下上传任何东西

### 4.3 一个 8 周的调研计划（可执行版）

| 周 | 动作 | 产出 |
| --- | --- | --- |
| 第 1 周 | 建"竞品差评库"，先抓 100 条 | `research/competitor-complaints.csv` |
| 第 2 周 | 补齐到 200+ 条，打标签做聚合 | 痛点排序表（Top 10） |
| 第 3 周 | 写好访谈提纲与知情同意 | 访谈脚本 |
| 第 4~5 周 | 深访 10 人（同学 / 群友） | 10 份访谈记录 + 归纳 |
| 第 6 周 | 发问卷（目标 100 份） | 问卷结论 |
| 第 7 周 | 把三份数据交叉验证，找出**重复出现 3 次以上**的结论 | 结论清单 |
| 第 8 周 | 据此重排里程碑，写进 ROADMAP | 迭代方向 |

> 注意：**第 7 周的"重复出现 3 次以上"是硬门槛**。
> 只在一处出现的说法只能进 Backlog，不能进路线图 —— 这是防止"被一个用户带偏"的纪律。

### 4.4 调研必须回答的 6 个问题

不问这 6 个，调研就是闲聊：

1. 你上一次打开课表 App 是**什么时候**？当时在干什么？（测真实频次）
2. 开学第 3 周之后你还会打开吗？为什么？（测留存衰减）
3. 你现在用什么替代？（截图 / 系统日历 / 教务 / 问同学）
4. 手动录 10 门课，你能忍吗？录到第几门会放弃？（测最大流失点）
5. 你愿意为**什么场景**付费？（问场景，不问功能）
6. 你最怕什么？（丢数据 / 隐私 / 广告 / 不准）

## 5. 由此确定的迭代方向

### 5.1 迭代优先级调整建议

现状（`docs/ROADMAP.md`）是 M2 → M3 → M4 → M5 → M6 → M7 → M8 顺序做。
基于上面的分析，我建议**重排**：

| 优先级 | 做什么 | 为什么排这个位置 | 成本 |
| --- | --- | --- | --- |
| **P0** | **M3 前半：iCal 日历订阅** | 用**最低成本**解决"没有闹钟"这个最大短板 —— 课表订阅到系统日历后，闹钟由系统负责，且锁屏可见、跨设备可见。同时它还顺手解决了"电脑和手机数据不通" | 低 |
| **P0** | **M2：安装引导 + 离线验证 + 字号/密度** | 直接影响留存，成本低 | 低 |
| **P0** | **M3 后半：兼容竞品导出文件的导入** | 命中 2.4 里最大的流失点（手动录课），且**合法绕开教务抓取** | 中 |
| **P1** | M7 笔记（**只做一种粒度**：绑定某一门课） | 课表是低频，笔记是高频；这是唯一能真正提升打开频次的功能。但**先做最小版**验证 | 中 |
| **P2** | M4 日程表 | 有价值，但不解决核心痛点，属于"扩张"而非"补短板" | 中 |
| **P3** | M5 闹钟（Capacitor 原生包） | 成本最高（需要 Android Studio 环境、要发版），只有在 iCal 方案被验证不够用时才做 | 高 |
| **P4** | M6 任务 | 与笔记有重叠，可合并考虑 | 中 |
| **P5** | M8 多设备同步 | 一旦做服务器，等于放弃"无服务器"这个最大卖点，**要极其慎重** | 很高 |

**核心变化：把 M3 提到 M2 之前/并行，把 M5 往后推。**
理由：M5（原生闹钟）成本最高、平台风险最大，而 iCal 订阅能用 5% 的成本拿到 70% 的效果。

### 5.2 三个"不要做"

历史已经替我们付过学费：

| 不要做 | 依据 |
| --- | --- |
| **不要做校园社交 / 匿名社区** | 课程格子的"Here"团队解散、超级课程表的"跳蚤市场"日发帖量跌到个位数；两家头部都在这上面翻过车。几微更没资源 |
| **不要做电商 / O2O 导流** | 学生"本身不具备任何忠诚度，谁便宜买谁"（原话出自出处一），这条路需要烧钱 |
| **不要为了留存而堆功能** | 竞品差评里"与课表无关的东西太多了"是高频抱怨。"轻"是几微唯一的护城河，堆功能等于自杀 |

### 5.3 如果要找"第二曲线"

正确的扩张方向是**把"课表"扩展成"学期"**，而不是扩展成"校园"：

```
课表  →  日程  →  任务  →  笔记
（我在哪上课）（我要去哪）（我要交什么）（我学到了什么）
        ↑ 全部围绕"我自己这一个学期"展开
```

而**错误**的方向是：

```
课表 → 校园社交 / 二手市场 / 兼职 / 表白墙   ← 历史证明全部失败
```

判断标准很简单：**新功能是回答"我这学期发生了什么"，还是回答"别人在干什么"？**
前者做，后者不做。

### 5.4 应该盯什么指标

课表 App **不能看 DAU**（它本来就低频）。应该看：

| 指标 | 为什么 | 健康线（建议，待验证） |
| --- | --- | --- |
| **开学第 4 周留存** | 直接测"是不是只用一次就丢" | > 60% 算好 |
| **备份导出率** | 测信任度：愿意为它做备份，说明真的在用 | > 20% 算好 |
| iCal 订阅使用率 | 测 P0 方案是否命中痛点 | > 30% 说明方向对 |
| 手动录课完成率 | 测 2.4 的最大流失点 | 录满 5 门的人占比 |
| NPS（愿意推荐给同学吗） | 口碑是唯一推广渠道 | > 30 |

> **不要**用"总注册数""下载量"这类数字自我安慰 —— 本项目连账号都没有，这些数字也不存在。

# 几微 2.0 产品与插件化架构提案

> 状态：方向已确认（2026-10-01）。本文是产品与架构边界说明；只有已标注“当前状态”的内容代表已经实现，M2–M8 仍按路线逐步交付。
>
> 编制日期：2026-10-01（Asia/Shanghai）

## 1. 提案摘要

几微适合从“课程表应用”扩展为“围绕一个大学生学期的本地优先工作台”。课表仍然是入口，扩展方向只回答四类问题：

1. **我什么时候要去哪里？** 课程、日程、考试和地点。
2. **我接下来要完成什么？** 作业、截止日期、考试准备和轻量计划。
3. **我在这门课学到了什么？** 课程笔记、资料索引和复习回顾。
4. **我怎样把自己的数据带走或与可信的人协作？** 备份、标准格式导出、可撤销的分享和可选同步。

产品应继续把“本地、离线、无广告、不索要教务账号密码”作为默认承诺。云同步、持续日历订阅、班级协作和 AI 等能力可以成为明确的增值服务，但不能让本地核心失效，也不能把数据采集变成商业模式。

## 2. 对现有商业化分析的修正

`docs/产品分析.md` 对用户痛点和红线的判断很有价值，但其中有三处需要在实施前校准：

| 原判断 | 提案中的修正 | 影响 |
| --- | --- | --- |
| iCal 订阅成本低，能顺手解决跨设备 | 本地生成 `.ics` 文件是低成本；**长期订阅 URL**需要可持续的托管、更新、撤销和隐私保护 | M3 先交付文件导出与本地分享；托管订阅放到有明确服务成本和权限模型的阶段 |
| iCal 能解决“电脑和手机数据不通” | 它只能把已发布的事件送入日历，不能把用户在另一台设备的编辑同步回几微 | 不把日历订阅宣传成同步；同步仍属于 M8+ 的独立能力 |
| 云能力适合买断 | 服务器、存储、推送和带宽是持续成本；买断只适合有限期限或自托管导出 | 云同步与持续订阅采用成本透明的可选方案，必要时提供导出和删除入口 |

iCalendar 是标准的交换格式，支持事件、待办、日志和提醒等对象；重复课的停课例外可以用 `EXDATE` 表达。系统日历通常把 URL 订阅视为只读外部日历，因此“订阅”与“回写同步”必须分开描述。[RFC 5545](https://www.rfc-editor.org/rfc/rfc5545)；[Apple 外部日历订阅说明](https://support.apple.com/guide/iphone/iph3d1110d4/ios)

## 3. 产品边界与目标用户

### 3.1 目标用户

- 想要干净、可靠、少打扰工具的本科生和研究生。
- 需要处理单双周、多校区、临时调课、考试与作业截止日的人。
- 愿意手动录入或从其他应用导出文件，不愿交出教务账号密码的人。
- 需要把课表、任务和笔记放在同一个学期语境中，但不想使用臃肿通用效率工具的人。

### 3.2 明确不服务的方向

- 校园匿名社区、信息流、二手市场、兼职和 O2O 导流。
- 任何索要教务系统密码、自动化模拟登录或未经授权抓取的导入方式。
- 广告 SDK、设备指纹、默认开启的行为追踪和出售用户数据。
- 以“AI”作为首页中心的聊天入口。AI 只能在用户主动提供内容后做本地或明确授权的辅助。

### 3.3 产品承诺

| 承诺 | 验收方式 |
| --- | --- |
| 没网仍能看、改和导出本地数据 | 浏览器离线、原生离线和恢复测试 |
| 核心功能无账号、无广告 | 首次启动和网络断开时均可使用 |
| 数据可带走 | JSON 全量备份、标准 CSV/ICS/Markdown 导出可回读 |
| 每一次上课时间有唯一真相 | 所有模块复用 `packages/core` 的展开与时区函数 |
| 插件权限可见、可撤销 | 安装前权限清单、运行时能力降级、卸载清理 |

| 任务 | 知道最近要交什么 | 截止日期、状态、按课程归属、冲突提示 | P1 | 本地 `Block(kind=task)` | 免费核心；团队协作另计 | M6 计划 |
| 课程笔记 | 把一次课和复习材料联系起来 | 课程级/单次课/独立 Markdown 笔记、标签、搜索 | P1 | 本地正文和附件；用户可导出 | 免费核心；可选 AI 处理按次或本地执行 | M7 计划 |
| 提醒 | 在合适的时间被提醒 | 应用内提醒、ICS 提醒偏移；能力不足时显示限制 | P1 | 本地规则 `Alert` | 免费核心 | M5 计划 |
| 原生闹钟 | 锁屏后仍可靠提醒 | Capacitor 本地通知、权限与电池优化引导 | P1 | 本地排程，不默认上传课程 | 一次性原生增强版或免费开源；不按提醒次数限额 | M5 计划 |
| 学期首页 | 打开就知道今天最重要的事 | 可排序 widgets：下一节、待办、考试、最近笔记 | P1 | 只读组合各模块查询 | 免费核心 | 架构已有雏形，未完整实现 |
| 分享课表 | 给班委/同学一份可撤销视图 | 静态图片、脱敏 ICS、短期只读链接 | P2 | 明确选择字段与有效期 | 班级/社团版可收费 | M8+ |
| 多设备同步 | 手机和电脑保持一致 | 端到端加密或最小字段同步、冲突预览、随时导出 | P2 | 明确服务器、账号、删除和迁移 | 可选订阅或自托管；不影响离线核心 | M8+ |
| 开发者插件 | 扩展而不改核心 | 先做内置模块契约，再做受限第三方插件 | P2 | 权限、版本、数据命名空间 | 插件市场/专业插件待验证 | 本提案新增 |
| AI 辅助 | 总结、生成复习卡、规划学习 | 用户主动选择的文本处理；显示输入、输出和删除方式 | P2 | 默认本地；云端需逐次同意 | 按次/自带 Key/订阅，绝不默认上传 | 待研究 |

### 4.1 推荐的用户主流程

```text
导入或快速录入课程
        ↓
今天/下一节课 + 系统日历
        ↓
考试与截止日 → 任务 → 课程笔记
        ↓
学期结束：导出备份、ICS、Markdown
        ↓
需要时再选择同步、分享或原生能力
```

这条流程让高频功能（任务、笔记、复习）围绕已有的课程语境增长，同时不把社区和无关内容塞进首页。

## 5. 插件化分层方案

“插件化”不应一开始就等同于“任意网页代码可以运行”。建议分三层逐步开放：

### L0：内置功能模块（现在可做）

继续使用当前 `FeatureModule` 注册表。`timetable`、`calendar`、`tasks`、`notes` 都是独立 feature，外壳只读取 `id/title/icon/order/render/widgets/setup`。模块之间不直接 import，跨模块通过 core 类型、只读查询和事件总线协作。

### L1：受控扩展包（M4–M7 期间验证）

扩展包以版本化 manifest 描述，不允许执行任意远程 JavaScript：

```ts
interface ExtensionManifest {
  id: string                 // 反向域名或 npm 风格命名空间
  version: string            // SemVer
  apiVersion: 1
  name: string
  permissions: Array<'read:blocks' | 'read:occurrences' | 'write:blocks' | 'write:notes' | 'notifications' | 'files'>
  contributes: Array<'module' | 'widget' | 'parser' | 'exporter' | 'theme'>
  dataNamespace: string
  entry: string              // 仅指向本地打包资源或经审核的扩展包
}
```

安装流程：查看 manifest 与权限 → 用户确认 → 校验签名/哈希 → 解压到本地扩展目录 → 运行迁移 → 显示可撤销权限。卸载时运行反向迁移并清理该 `dataNamespace`，核心数据不被删除。

### L2：沙箱插件（有真实生态需求后再做）

第三方插件只能通过窄 API 访问数据和能力，默认无网络、无 DOM、无任意文件路径访问。Web 端可考虑 Worker/受限 iframe，原生端使用独立 JS runtime 或 Capacitor bridge；不能把 `iframe` 当成完整安全边界。若使用 iframe，必须采用独立 origin、严格 CSP 和 sandbox，避免同时授予可逃逸的脚本与同源权限。[MDN iframe sandbox 说明](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe)

建议第一批插件类型仅开放：

- `parser`：把用户选定的 CSV/竞品导出文件转换成标准 `BlockDraft`；
- `exporter`：输出 Markdown、ICS 或图片；
- `widget`：只读展示课程、任务或笔记摘要；
- `theme`：只提供 CSS 变量，不接触数据。

暂不开放任意后台任务、网络抓取、教务登录、全库写入、支付和账号权限。这样能把插件生态的价值放在“转换和展示”，不会绕过产品红线。

### 6.2 关键数据与事件

- `Block` 仍是课程、日程、任务和考试共享的时间实体；`Occurrence` 仍是提醒、笔记和冲突的锚点。
- `PluginData`（建议新增）按 `extensionId + dataNamespace + key` 隔离，插件不能把自定义字段写入核心表。
- 业务写入通过 application use case 完成：`importBlocks`、`moveOccurrence`、`completeTask`、`attachNote`；插件拿不到 Dexie 实例。
- 事件总线只发布领域事件，如 `block.created`、`occurrence.materialized`、`task.completed`、`backup.restored`。事件载荷使用 core 类型，禁止传递数据库对象。
- `refresh()` 仍只更新读取信号；恢复和批量写入必须在事务成功后发布一次事件并同步选中学期状态。

### M8 的商业闸门

只有同时满足以下条件，才进入云同步或班级协作：

1. 真实访谈/反馈中有重复出现的跨设备或协作需求；
2. 已能说明每个账号、设备、存储和推送成本；
3. 用户能随时导出、删除和停止同步；
4. 本地核心在服务器不可用时仍可读写；
5. 付费购买的是持续服务，不是把原有的离线功能锁起来。

## 8. 已确认的产品边界

1. **插件层级**：先做 L0 内置模块，M7 再验证 L1 受控扩展，暂不做任意第三方远程代码。
2. **功能优先级**：导入/备份与 ICS 先于日程、任务、笔记；不把云同步提前到 M3。
3. **商业边界**：本地核心永久免费、无广告；只对持续成本明确的同步、托管订阅或协作收费。
4. **AI 边界**：默认关闭，优先本地或逐次同意；不把课程内容或笔记默认上传。
5. **推进方式**：先把“今天”和课程表做成稳定可用的应用，其他模块先提供入口和空状态，再逐阶段实现。

### 10.1 新的产品组合

| 模块 | 必须解决的场景 | 第一版边界 | 备注 |
| --- | --- | --- | --- |
| 课程表导入 | 不想逐门录入课程 | 图片识别课程表 + CSV/JSON/竞品导出文件；全部先进入预览和人工确认 | AI 只生成草稿，不直接写入正式课表 |
| 记账 | 快速记录支出和收入 | 金额、收支方向、分类、商户、日期、备注、附件、月度汇总 | 本地数据优先；发票/小票图片属于敏感数据 |

| 手写笔记 | 课堂上直接写 | 笔画、橡皮、撤销、页面和图片附件；可导出原图/PDF | 先做手写画布，不把手写识别当成前置条件 |
| 文字记录 | 随手记下想法和课堂内容 | Markdown/纯文本、标签、课程/课次关联、搜索 | 手写与文字可放在同一条笔记中 |
| 待办 | 知道下一件要完成的事 | 标题、截止日期、优先级、课程关联、完成状态 | 后续再做子任务和重复规则 |
| 今日总览 | 一眼看到今天的生活学习负担 | 今日课程、待办、支出/收入、考试/日程、快速添加入口 | 只做聚合视图，不复制各模块数据 |
| AI 小助手 | 用一句话添加事项 | 识别“记一笔支出/加待办/记日程/写笔记/导入课程”意图并生成草稿 | 涉及写入、图片或联网的动作必须二次确认 |

推荐的首批官方模块为：`timetable`、`ledger`、`notes`、`tasks`、`agenda`、`assistant`。官方模块按需启用；开发者插件延后到受控扩展 API 稳定后开放。

### 10.2 AI 与识图的安全工作流

```text
用户输入文字/图片
        ↓
本地 OCR 或用户明确同意的云端 OCR
        ↓
结构化草稿（字段 + 置信度 + 原图引用）
        ↓
用户预览、修改、确认
        ↓
application use case 写入核心仓储
        ↓
发布领域事件并刷新今日总览
```

助手不能直接调用 Dexie、不能绕过表单校验、不能默认上传图片，也不能以聊天回复代替写入成功。每次执行都应生成可撤销的命令记录。课程表图片和小票识别要共享 `OcrAdapter`，但使用不同的领域解析器：`CourseTableParser` 输出 `BlockDraft[]`，`ReceiptParser` 输出 `TransactionDraft`。

原生端可优先使用设备端文字识别能力；Apple Vision 明确支持在设备上进行多语言文本识别，Google ML Kit 也提供设备端文字识别 API，这有利于离线和隐私，但中文课程表、手写字和复杂小票仍需用真实样本验证，不应把“有 OCR API”写成“识别一定准确”。[Apple Vision](https://developer.apple.com/documentation/vision/recognizing-text-in-images)；[Google ML Kit](https://developers.google.cn/ml-kit/migration?hl=en)

### 10.3 建议新增的领域模型

不立即改代码，先冻结语义：

```ts
Transaction {
  id, type: 'income' | 'expense', amount: string, currency,
  occurredAt, category, merchant?, note?, attachmentIds[], source,
  createdAt, updatedAt
}

NotePage {
  id, noteId, kind: 'text' | 'ink' | 'mixed',
  text?, strokes?, imageIds[], order
}

AssistantDraft {
  id, intent: 'courseImport' | 'transaction' | 'task' | 'event' | 'note',
  inputRefs[], fields, confidence, status: 'draft' | 'confirmed' | 'rejected'
}
```

金额用十进制字符串或最小货币单位保存，避免 JavaScript 浮点误差。图片与手写笔画放在附件/内容仓储，核心表只保留引用和元数据。`Transaction`、`NotePage` 和 `AssistantDraft` 都必须参与 JSON 备份与删除恢复测试。

## 11. 完全月租制与替代方案分析

### 11.1 完全月租制为什么有合理性

完全月租适用于持续产生成本的能力：云端 AI 识图、跨设备同步、托管 ICS、推送、协作和客服。它能带来可预测收入，使服务端存储、模型调用和持续维护有预算；多月订阅还能降低每次续费的操作成本。Apple 和 Google 都提供自动续订订阅机制，但商店服务费会直接减少开发者所得；Apple 文档说明通常首年按 70% proceeds 计算，小型开发者计划或续订满一年后可到 85%，Google Play 当前文档对自动续订订阅列出 15% 服务费。[Apple 订阅](https://developer.apple.com/app-store/subscriptions/)；[Google Play 服务费](https://support.google.com/googleplay/android-developer/answer/112622)

### 11.2 对几微的主要问题

| 风险 | 为什么对几微更明显 | 结果 |
| --- | --- | --- |
| 使用季节性 | 课程表在开学前后最常用；考试、记账和笔记可能持续，但未验证 | 月租容易在假期被取消 |
| 价值与成本错配 | 本地课程表、手写、文字笔记和基础记账没有持续服务器成本 | 为本地能力强制月租会违背“本地优先、干净免费”的信任基础 |
| 学生支付阻力 | 学生会比较通用日历、备忘录、记账 App 和免费 OCR | 首次转化、续费和口碑压力都高 |
| 订阅疲劳 | 用户已有多个影音、学习和效率订阅 | 需要持续解释“本月为什么值得续费” |
| 平台复杂度 | PWA、App Store、Google Play 的购买、恢复购买和跨端权益不同 | 账号、支付和客服工作会提前挤占产品开发 |
| AI 成本波动 | 图片大小、模型和重试次数会让单用户成本不稳定 | 不能无限量承诺 AI 识图；需要公平使用策略 |

结论：**完全月租可以作为云增强版的商业模式，但不适合作为整个几微的唯一入口，也不应锁住本地课程表、待办、笔记和基础记账。**“多月一订”比纯月租更适合学期型产品，但必须允许暂停、取消、导出和降级到本地模式。

### 11.3 推荐的替代方案

| 方案 | 用户购买什么 | 好处 | 代价/限制 | 推荐度 |
| --- | --- | --- | --- | --- |
| 本地永久免费 + 云增强月租 | 同步、云端 OCR、AI 助手、托管 ICS、分享 | 保留信任；收入与持续成本对应；低门槛试用 | 需要清楚区分本地与云端状态 | **最高** |

| 自托管/自带 Key | 用户自己承担服务器或模型费用 | 适合技术用户和开源社区，降低平台成本 | 普通学生配置门槛高；不能作为默认路径 | M8+ |

## 12. 架构就绪度审计：模块开关与 AI

### 12.1 当前结论

当前架构**部分具备基础，但还不能承诺未来所有功能都已经插件化**。

已经存在的基础：

- `apps/web/src/modules.ts` 有静态 `FeatureModule` 注册表，外壳通过模块渲染页面；新增官方模块不需要把业务代码塞回 `App.tsx`。
- `packages/ui/src/module.ts` 已有 `id/title/icon/order/render/widgets/setup` 契约，适合先承载官方模块和首页卡片。
- `Block + Occurrence` 可以统一承载课程、日程、任务、考试，`Note`、`Alert` 已预留关联点。
- `packages/data` 的仓储接口和 `packages/platform` 的能力适配层为存储、文件、通知和原生能力隔离了实现细节。

仍然缺少的闭环：

- 没有持久化的模块启用状态、依赖检查、版本迁移和禁用后的数据处理策略。
- `setup` 当前没有稳定的 `AppContext`，模块仍可能直接组合仓储调用，缺少统一的应用用例和领域事件边界。
- 没有第三方扩展的 manifest、权限、签名/哈希校验、安装卸载、沙箱和数据命名空间实现。
- 没有 AI provider、结构化意图、工具调用、用户确认、审计记录和用量控制。

因此，提案中的插件化和 AI 设计属于**下一步要落地的架构增量**，不是当前仓库已经完成的功能。

### 12.2 官方模块开关的落地方案

建议把现有 `FeatureModule` 扩展为 manifest + runtime 两部分：

```ts
interface ModuleManifest {
  id: string
  version: string
  kind: 'official' | 'extension'
  title: string
  defaultEnabled: boolean
  dependencies?: string[]
  permissions: Permission[]
  dataNamespace: string
  contributes: Array<'page' | 'widget' | 'parser' | 'exporter' | 'assistantTool'>
}

interface ModuleRuntime {
  manifest: ModuleManifest
  render: ComponentType
  widgets?: WidgetDef[]
  setup?(ctx: AppContext): void | Promise<void>
  teardown?(ctx: AppContext): void | Promise<void>
}
```

新增 `ModuleManager`，职责固定为：

1. 读取模块注册表和 `Meta` 中的 `module:<id>` 设置；
2. 校验依赖、版本和平台能力；
3. 启用时执行迁移和 `setup`，禁用时执行 `teardown`；
4. 只把已启用模块交给导航和首页 widget；
5. 卸载扩展时按 `dataNamespace` 清理扩展数据，核心课程、账目和笔记必须由用户另行确认；
6. 对缺失依赖、迁移失败和权限拒绝给出可恢复错误。

模块开关的用户语义要分成三种：

| 操作 | 行为 |
| --- | --- |
| 隐藏 | 保留数据和设置，不显示导航/widget |
| 停用 | 停止后台任务和通知，保留数据，之后可重新启用 |
| 卸载扩展 | 删除扩展代码；先导出或确认清理扩展专属数据 |

官方模块可以静态打包、按需启用；第三方插件必须经过 manifest、权限和版本检查。这样既满足功能开关，也避免把“隐藏页面”误称为“安全插件系统”。

### 12.3 AI 的明确架构

AI 不直接写数据库，而是一个位于 `application` 层的“草稿生成器 + 受控工具调用器”：

```text
输入：文字 / 图片 / 当前页面上下文
                ↓
InputNormalizer（裁剪、压缩、脱敏、OCR）
                ↓
IntentRouter（识别任务类型）
                ↓
AiProvider（本地模型 / 云模型 / 无 AI 降级）
                ↓
Zod 结构化 Draft + 字段置信度 + 原始引用
                ↓
Preview / Edit / Confirm
                ↓
Application Use Case（唯一写入口）
                ↓
Repos 事务写入 + Domain Event + 可撤销记录
```

第一批固定意图，不允许模型自由生成数据库操作：

```ts
type AssistantIntent =
  | { type: 'courseImport'; draft: CourseImportDraft }
  | { type: 'createTransaction'; draft: TransactionDraft }
  | { type: 'createTask'; draft: TaskDraft }
  | { type: 'createEvent'; draft: EventDraft }
  | { type: 'createNote'; draft: NoteDraft }
```

每个意图对应一个白名单 use case，例如 `importCourses`、`createTransaction`、`createTask`。模型只负责提出结构化参数，use case 负责 schema 校验、权限检查、冲突检查、事务写入和撤销信息。

### 12.4 AI provider 与隐私策略

```ts
interface AiProvider {
  id: string
  capabilities: Array<'ocr' | 'courseParse' | 'receiptParse' | 'textAssist'>
  locality: 'device' | 'selfHosted' | 'cloud'
  analyze(input: AiInput, schema: StructuredOutputSchema): Promise<AiResult>
}
```

建议提供三种实现：

- `LocalProvider`：规则、设备端 OCR、可用时的本地模型；默认路径，支持离线。
- `CloudProvider`：用户逐次同意后上传必要图片/文字；显示供应商、字段、保留时间和用量。
- `NoAiProvider`：AI 不可用时回到手动表单、CSV/JSON 导入和普通文字输入。

OCR 与大模型分离：课程表和小票首先经过 `OcrAdapter`，结构化解析可以由规则/本地模型完成；复杂总结和自然语言改写才调用 LLM。这样可以控制成本，也能让敏感图片尽量留在设备上。

必须遵守以下规则：

- 默认关闭云端 AI，不把账单、课程表、笔记上传作为启用模块的隐含条件。
- 课程批量导入、财务记录、带图片的上传和批量修改始终需要用户确认。
- 识别结果显示置信度、原始图片或文本引用和可编辑字段。
- 每次 AI 写入产生可撤销命令；失败、超时和重复请求必须幂等。
- AI 用量由 `AiUsagePolicy` 统一管理，支持本地免费、学期额度、按量包和月租权益；插件不能自行保存平台 API Key。
- 不把模型回答作为事实来源；涉及金额、日期、课程时间和提醒时，以结构化数据校验结果为准。

### 12.5 插件与 AI 的关系

第三方插件只能通过受控 `assistantTool` 声明扩展 AI 能力，例如“把某种格式解析成课程草稿”。插件不能直接调用模型、读取全部笔记或写入账目；它必须申请最小权限，并返回版本化的结构化结果。官方 `assistant` 模块负责统一确认、计费、日志和隐私提示。

完成上述 `ModuleManager`、`AppContext`、`Application Use Case`、`AiProvider` 和 `AssistantDraft` 后，才可以说架构真正为“官方模块按需启用、未来开发者插件、AI 辅助写入”打好了基础。
