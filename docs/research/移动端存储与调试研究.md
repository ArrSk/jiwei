## 零、一句话结论

架构的**分层是对的**，但有几处"为将来准备的东西"和"手机真正需要的东西"错位了：

| 判断 | 结论 |
| --- | --- |
| `@jiwei/core`（纯模型 + 时间函数） | ✅ **最该有的部分，做得对**，不要动 |
| `@jiwei/data`（仓储接口 + 可替换引擎） | ✅ 对，且已实测能换引擎（ADR-007） |
| `@jiwei/platform` 能力适配层 | ⚠️ **抽象错了对象**：定义了 Web 永远做不到的事（闹钟），却没承载手机真正的关注点 |
| `@jiwei/ui` 组件库 | ⚠️ **样式契约是松的**：DOM 在包里、样式类在 web 端，包不自洽 |
| 模块注册表 `FeatureModule` | ⚠️ 成本低但**收益未经验证**（至今仍只有一个模块） |
| **调试能力** | ❌ **最大的短板**：我改完 UI 看不到结果，全靠你拍照反馈 |

## 一、最大的短板：没有"看一眼"的能力

这是过去十几轮里**真正的瓶颈**，比架构问题更值钱：

- 左边轴消失 → 你发现
- 表头被课程块盖住 → 你发现
- 时间显示不全、字太小 → 你发现（而且我当时以为改了，其实 **UI 包里样式失效**，见 DESIGN-VERSIONS 第八节）
- 课程名被截断 → 你发现

**每一次都是你截图我才知道。** 一个 UI 密集的项目，靠"改完 → 用户看 → 用户描述 → 再改"的循环，
每个问题至少花掉一个来回，而且我无法自己判断"间距够不够、字挤不挤"这类主观项。

### 已完成的改进：独立静态产物服务

新增 `scripts/serve-dist.mjs`（零依赖）：

```powershell
pnpm build
node scripts/serve-dist.mjs 4173      # → http://127.0.0.1:4173/
```

**价值**：不经过 Vite/esbuild，因此**不受本机沙箱的 EPERM 限制**，
任何自动化检查（浏览器、断言脚本、手机）都能指向一个稳定地址看**产物真实行为**
（而不是带 HMR 的 dev server）。这一条对手机验收也有用：手机上开 `http://<局域网IP>:4173/`
看到的就是打包后的真实效果。

### 尝试但受阻：无头浏览器截图

已确认系统装了 **Edge**（`C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe`），
本可绕开 Playwright 的 150MB Chromium 下载，用 **CDP 协议 + Node 自带 WebSocket**（零依赖）截图。

写了 `scripts/shot.mjs`，但**在当前沙箱下走不通**：浏览器进程能启动，
但调试端口不监听、`--dump-dom` 也返回空，crashpad 报 `OpenProcess: 拒绝访问`。
与 vite / vitest 同一类边界（受限模式拒绝子进程与套接字）。

**结论**：截图能力是**值得投入但当前环境受限**的事。
两条可行路径（见第四节）。

## 三、架构优化建议（按性价比排序）

### P0 · 把手机真正的关注点收进 `platform` 层

**现状**：`packages/platform` 定义了 `alarm` / `notifications` / `storage` / `files`，
其中 `alarm` 在 Web 端**永远是 `canAlarm: false` 的桩**（M5 才用）。
与此同时，手机上真正折磨人的东西散落在各组件里：

- 安全区（`env(safe-area-inset-*)`）→ 现在写在 `styles.css` 与 `CourseForm` 里
- 软键盘弹起时的布局变化 → 现在靠"不自动聚焦"绕开
- 触摸目标尺寸 → 每个组件自己拍脑袋定
- 返回键 / 手势返回 → 完全没处理（Android 上会很突兀）

**建议**：`platform` 增补 `viewport` / `keyboard` / `haptics` / `backButton` 能力，
把"手机适配"变成一层可测的能力，而不是散落的魔法类名。

### P0 · 让 `@jiwei/ui` 自洽（修样式契约）

**现状**：`TimeGrid.tsx` 输出 `tg-cell`、`tg-cell--alt`、`tg-cell--today` 这些类名，
而样式定义在 **web 端的 `styles.css`**。后果：

1. 任何新的宿主（比如将来的 `apps/native` 或 Storybook）都必须记得引入这份 CSS，否则组件裸奔；
2. 更难察觉的是——**Tailwind 扫描问题正是这个契约导致的**（DESIGN-VERSIONS 第八节）：
   包里的类名能不能生成取决于宿主配置。

**建议**：二选一
- **A（推荐）**：把 `TimeGrid` 的少量关键样式内联为 `style` / CSS-in-JS，只保留 Tailwind 的布局工具类；
- **B**：`@jiwei/ui` 自带一份 `styles.css`，由包导出，宿主 import。

### P1 · 加"日视图"，同时解决触摸目标与文字拥挤

手机上一列只有约 **45px**，这是七个列宽共存的物理上限。它带来两个无法同时解决的问题：
文字要小（现在 11px，每行约 4 字）、格子要好点（45px 勉强达标）。

**日视图（一列铺满屏宽 ≈ 330px）能同时解决两者**：字可以放大到 14–15px、
完整显示课程名与地点、点按区域大 7 倍。参考的两个成熟课表 App 也都有日视图。

> 这条与你之前"要在手机上一屏看全 7 天"的要求冲突，因此**只作为建议**，
> 建议形态是：**默认周视图，点某天进日视图**，而不是替换。

### P1 · 修掉那两个具体缺口

- `SettingsPage` 底部加 `env(safe-area-inset-bottom)`
- 触摸目标：把课表格子的最小高度从 `clamp(3rem,…)` 提到确保 ≥44px

### P2 · 重新审视 `FeatureModule` 注册表

它现在只是"把一个组件包成对象"。**在第二个模块真实落地前，"加模块不用重构"是未经验证的假设**。
建议：M4 日程模块落地时，把这次验证结果写回 `DECISIONS.md`（若发现契约要改，现在改便宜）。

### 保持不动

- `@jiwei/core` 与 `@jiwei/data` 的划分 —— 已被 63 个单测与两次引擎切换验证过
- 仓储接口隔离（ADR-007）—— 它让"换存储"从重构降级为换一个入参
- 不做服务端（ADR-002）—— 单用户场景下这是对的

## 四、更好的调试方式（分三层，按可落地性排序）

### 第 1 层 · 你自己在手机上调试（现在就能用，零成本）

**A. 应用内调试面板**：在 `index.html` 里按需注入 [eruda](https://github.com/liriliri/eruda)
或 vConsole，手机上直接看 console、网络、DOM、存储。建议做成"仅 dev 构建注入"，不污染生产包。

**B. 远程调试**（最接近桌面体验）：

| 平台 | 做法 |
| --- | --- |
| Android / Edge | 手机开 USB 调试 → 电脑 Edge 打开 `edge://inspect`（Chrome 用 `chrome://inspect`） |
| iOS | 手机设置 → Safari → 高级 → 打开"网页检查器"；Mac 上 Safari → 开发 → 选设备 |

**C. 产物直连手机**（验收打包后行为）：

```powershell
pnpm build
node scripts/serve-dist.mjs 4173
# 手机同一 Wi-Fi 打开 http://<本机局域网IP>:4173/
```

### 第 2 层 · 让我能自己看（需要一次授权）

把 `scripts/shot.mjs` 跑起来（它已写好，只差权限）：用系统 Edge + CDP，
在 **390×1400 手机视口**下截图 + 输出页面探针（网格列数、轴文字、是否横向溢出）。

```powershell
node scripts/shot.mjs --url http://127.0.0.1:4173/ --out shot.png --width 390 --height 1400
```

**收益**：以后我改完 UI **自己先看**，把"布局坏了"这类问题在上报给你之前拦掉。

### 第 3 层 · 布局回归检查（不依赖截图）

比截图更稳定：用脚本断言**结构与计算样式**，例如
"网格必须是 8 列"、"左侧轴第一格文字以 `08:00` 开头"、"`scrollWidth <= innerWidth`（不横向溢出）"。
这类断言在 CI 里跑得动，也不会因为渲染像素差异而误报。

> 我已在 `scripts/shot.mjs` 里内置了探针输出（`--probe`），可直接扩展成断言脚本。

### 前置依赖

第 2、3 层都需要一个**能跑浏览器的环境**。当前沙箱受限；
可选：① 每次给我一次完全访问授权；② 你在自己终端跑这两条命令（不受沙箱约束）。

## 1. Capacitor 应用里 IndexedDB / WebView 存储的持久性

### 结论

1. **Capacitor 官方明确表态：LocalStorage「必须当作临时数据」，并明确说 IndexedDB 至少在 iOS 上同样如此。** 这是本项目最需要正视的一条官方结论——它直接否定了「用 IndexedDB 存不能丢的数据」这个前提。
2. **Android 与 iOS 的差异是真实存在的**：官方原文指出 Android 上可以用 **Persisted Storage API**（`navigator.storage.persist()`）把 IndexedDB 标记为持久化，**iOS 则不行**。所以在 Capacitor 里 IndexedDB 的"抗清理"能力是平台不对称的。
3. **iOS 打包成原生 App 后，ITP 的"7 天清理"并不适用**——WebKit 官方博客与 Bugzilla 都说明：加到主屏幕的 Web App 有独立的"使用天数"计数器，**不会**因为 7 天不用而被删；而且 WebKit 工程师明确说对 WebView 没有豁免开关，唯一要求是 `display` 用 `standalone`/`fullscreen`。**但 ITP 不是本项目的主要风险**，主要风险是下面第 4 点。
4. **真正的杀手是 iOS 的 IndexedDB 连接丢失 bug（不是"数据被清理"，而是"连不上 → 写入静默失败 → 数据真丢"）**。WebKit Bugzilla #277615 是一条跨越 2024-08 到 2026-03 的长线程，**举报者与多名评论者明确说自己是 Capacitor 应用**，症状是 app 后台挂几小时后回前台，`UnknownError: Connection to Indexed Database server lost.`，**无法恢复**，用户必须强杀 App；有人统计到 24 小时内 iOS 18.3/18.4 上分别 33635 / 32616 次失败。WebKit 工程师最终定位为"WebKit network process 被内存压力杀掉"，并承认第二个子问题（连接无法重连）**已在 #309386 修复**。
5. **社区有大量真实数据丢失/不可用报告**，而且**多人在同一线程里说"我们迁移到 SQLite 了"** ——这是本次调研中最有说服力的迁移理由。

### 证据与出处

**A. Capacitor 官方 Storage 指南（v8 版本文档）** — <https://capacitorjs.com/docs/guides/storage>

原文关键句（逐字）：

> "Local Storage can be used for small amounts of temporary data, such as a user id, but **must be considered transient**, meaning your app needs to expect that the data will be lost eventually. This is because **the OS will reclaim local storage from Web Views if a device is running low on space**. **The same can be said for IndexedDB at least on iOS (on Android, the persisted storage API is available to mark IndexedDB as persisted).**"

同一页对 Preferences 的定位（逐字）：

> "Capacitor comes with a native Preferences API that **avoids the eviction issues above**, but is meant for **small amounts of data**. The Preferences API provides a simple key/value API with **no advanced query support**."

同一页关于"大数据/高性能"的推荐（逐字）：

> "The most widely supported option is **SQLite**. There are a number of community-maintained SQLite plugins that should work in Capacitor, including [capacitor-sqlite](https://github.com/jepiqueau/capacitor-sqlite) and [cordova-plugin-sqlite](https://github.com/xpbrew/cordova-sqlite-storage)."
> "The Capacitor team also offers an **enterprise SQLite storage solution** with encryption support…"（即官方 SQLite 能力走 Ionic Enterprise 商业线，见问题 2）

**B. WebKit 官方博客《Full Third-Party Cookie Blocking and More》（2020-03-24，ITP 7 天上限的权威出处）** — <https://webkit.org/blog/10218/full-third-party-cookie-blocking-and-more/>

原文关键句（逐字）：

> "Now ITP has aligned the remaining script-writable storage forms with the existing client-side cookie restriction, **deleting all of a website's script-writable storage after seven days of Safari use without user interaction on the site**. These are the script-writable storage forms affected…: **Indexed DB / LocalStorage / Media keys / SessionStorage / Service Worker registrations and cache**"
>
> "**A Note On Web Applications Added to the Home Screen** … **Web applications added to the home screen are not part of Safari and thus have their own counter of days of use.** Their days of use will match actual use of the web application which resets the timer. **We do not expect the first-party in such a web application to have its website data deleted.** If your web application does experience website data deletion, please let us know since we would consider it a serious bug."

**这意味着**：ITP 的 7 天清理针对的是 Safari 标签页里的脚本可写存储；打包成 Capacitor 原生 App 后不是"Safari 站点"，因此 7 天规则不构成主要威胁。

**C. WebKit Bugzilla #232302（"PWA 加主屏后 7 天数据被删"，RESOLVED WONTFIX）** — <https://bugs.webkit.org/show_bug.cgi?id=232302>

WebKit 工程师 John Wilander 的官方回复（逐字）：

> "**There is no way to get an exception in Safari.** If you adjust your manifest to use either the **"standalone" or "fullscreen"** display mode, your home screen web application will open full-screen in Web.app and **you will get the behavior you want**."

即：WebView/独立窗口本身拿不到 ITP 豁免"开关"，但用 `standalone` 显示模式即可获得不受 7 天清理的行为。

**D. WebKit Bugzilla #277615 —— 本项目最关键的证据（Capacitor 场景的 IndexedDB 失效）** — <https://bugs.webkit.org/show_bug.cgi?id=277615>

标题：`IndexedDB failing with "UnknownError: Connection to Indexed Database server lost."`；状态 **RESOLVED DUPLICATE of #309386**。

举报者（2024-08-04，逐字）：

> "**My Capacitor (WebView in iOS app framework) app's** connection to IndexedDB will spontaneously close and fail to reopen, throwing this error… the bug still seems to happen **when the user uses the app, puts it into the background for a few hours, and then brings it back to the foreground**… it can't be fixed without the user force-closing and relaunching the app, and as a result, **I'm losing users**."

Dexie 作者 David Fahlander（2024-10-14，逐字，**直接关系到本项目的 Dexie 封装**）：

> "**Dexie.js is not able to workaround this issue.** Dexie.js has logic in place to re-execute transactions when certain errors happen. However, we've also tried whether **reopening the database helps in this case but unfortunately it does not**, making it impossible to work around this issue in Dexie.js or in IndexedDB-reliant apps."

其他 Capacitor 用户（逐字）：

> （评论 9）"I can also confirm that **our users get this error (capacitor)**… Sometimes it happens like every 24hrs, sometimes it just happens once in a whole week."
> （评论 14）"I ended up notifying the user to force close the app. It's a terrible user experience… Also AFAIK **localStorage is unaffected. Just Indexeddb.**"
> （评论 20，2025-05）"Still seeing this on iOS 18.4. Here are our failure counts by version in a recent random 24-hour period. **iOS 18.3 - 33635 / iOS 18.4 - 32616**"
> （评论 30，2025-11，**迁移结论**）"Yes sir, **we have successfully migrated to SQLite** with the default plugin as you mentioned [capacitor-community/sqlite]. It takes a short moment to initialize the database connection; you should strictly follow the example implementations in the repo. You should also consider to implement a **queue for your queries**, because penetrating the SQLite db with too many queries at the same time can lead to **OOM on Android really fast**."
> （评论 32，2026-03）"We did **switch to OPFS** in the meantime which has been working reliably for months."

WebKit 工程师 Sihui Liu 的官方定性（2026-03-26，逐字）：

> "the error shows up when **WebKit network process (responsible for storage operations) gets killed**… the most likely cause is **the process gets killed in the background due to memory pressure** (backgrounded and idle process has lower priority thus will be killed first). In this case, we would recommend **reopening connection and retry the operations**. (If you are app developer, you might want to see if you could **wrap up IDB operations when app enters background**, just to make sure the data is saved before process gets suspended; closing connection should not be required.) For [problem 2], we had a bug that underlying connection is not reset properly, and it **should be fixed after #309386**. We expect the fix to be **shipped in the coming release**."

**E. MDN《Storage quotas and eviction criteria》（best-effort vs persistent 的规范级说明）** — <https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria>

原文关键点（逐字）：

> "**Best-effort**: this is the way that data is stored by default. Best-effort data persists as long as **the origin is below its quota, the device has enough storage space, and the user doesn't choose to delete the data**…"
> "**Persistent**: … Data stored this way is **only evicted, or deleted, if the user chooses to**… developers … can do so by using the `navigator.storage.persist()` method"
> "**In Firefox**, when a site chooses to use persistent storage, the user is notified with a UI popup… **Safari and most Chromium-based browsers … automatically approve or deny the request based on the user's history of interaction with the site and do not show any prompts to the user.**"
> Web Storage 容量（逐字）："Web Storage … is **limited to 10 MiB of data maximum on all browsers**. Browsers can store up to **5 MiB of local storage, and 5 MiB of session storage per origin**."

注意：MDN 这一页描述了 `navigator.storage.persist()` 的通用规则，但**没有**针对 WKWebView / Capacitor 给出"是否生效"的说明（见最后一节）。

### 对本项目的建议

**优先级从高到低：**

1. **不要指望 IndexedDB 做课程表的唯一真源（single source of truth）。** 两个独立理由叠加：(a) 官方明说 IndexedDB 在 iOS 上必须当 transient；(b) 有跨 iOS 17.6 → 18.4 的实测 bug，且 Dexie 作者确认 Dexie **无法**规避。课程表恰好是"低频使用但绝不能丢"的数据——这个使用模式正好命中"后台几小时后回前台"的触发条件（学生一周只打开几次，但每次输入都要保留）。
2. **迁移到原生 SQLite（见问题 2），把 IndexedDB 降级为"Web 端适配层"。** 与 #277615 评论 30 的真实迁移案例一致。注意该用户给出的两条工程经验：**严格按官方示例初始化连接**、**给查询加队列（并发查询会很快在 Android 上 OOM）**。
3. **无论是否迁移，立刻补上"双写 + 导出"兜底**：
   - 写入课程表时同时写一份到 `@capacitor/preferences`（小体量 key/value，官方称其避开 eviction 问题）作为校验副本；课程表数据量本来就很小，非常适合。
   - 提供**手动导出/导入 JSON**（走 `@capacitor/filesystem` + `@capacitor/share`）。这是唯一能让用户在"数据已经出问题"之后自救的路径，成本极低。
4. **监听从 background 回前台，做一次 DB 健康检查**。#277615 评论 21 和 31 都指向这个方向：在 `App.addListener('appStateChange', ...)` 里先做一次轻量读操作，失败则提示/重建连接，而不是等用户点"添加课程"时才静默失败。**关键点：写入必须检查返回值**，绝不能 fire-and-forget——评论 6 提到 `idb-keyval` 在出问题时"read/write operations starts to fail **silently**"。
5. **不要用 localStorage 存课程表**（5 MiB 上限 + 官方定性 transient）。它只适合放"上次同步时间""主题偏好"这类可重建的数据。

## 2. Capacitor 官方 SQLite 与其他持久化方案的现状

### 结论

1. **没有"Capacitor 官方（Ionic 团队）开源的 SQLite 插件"。** 官方 Storage 文档只推荐社区插件，并另有一条 **Ionic Enterprise 商业 SQLite 方案**（带加密）。所以"官方 SQLite 插件"在开源侧不存在，这本身就是当前生态的既定事实。

5. **迁移成本/收益判断：对本项目，"为了数据不丢"值得迁移，但应当用薄封装而不是全量换 ORM。**

1. **目标架构（推荐）：原生端 SQLite 为主，Web/PWA 端保留 Dexie，用一层仓储接口（repository）隔离。**
   - Ionic 官方指南本身就推荐这个模式（"indexedDB on the web and … SQLite plugins on mobile"），说明这不是 hack。
   - 具体做法：定义 `CourseRepository` 接口（`listByWeek()` / `upsert(course)` / `delete(id)` / `replaceAll()`），写两个实现 `DexieCourseRepository` 和 `SqliteCourseRepository`，按 `Capacitor.isNativePlatform()` 选择。**不要让 UI 直接依赖 Dexie 的 Query 链**，否则迁移成本会失控。
2. **具体插件选择：`@capacitor-community/sqlite`（8.x，对齐你的 Capacitor 主版本），不要用 `@capawesome/capacitor-sqlite-drizzle`。** Drizzle 适配器还在 `0.0.1`、月下载 19 次，把它引入"数据不能丢"的关键路径上风险不成比例。课程表是极简的关系模型（课程、时间段、周次），手写 SQL + 参数绑定完全够用。
3. **迁移成本估算（基于本次查证到的事实）**：数据模型只有 2~3 张表；接口方法约 4~6 个；主要工作量在**双端一致性测试**和**首次启动的 IndexedDB → SQLite 一次性数据搬迁**。真正的坑是并发生命周期问题而非 SQL 本身——#277615 评论 30 明确警告 Android 上并发查询会 OOM，所以**仓储层要把查询串行化（一个 promise 队列）**。
4. **务必读并遵守官方示例的初始化顺序**（connection 初始化要 await 完整，不要并行 create/open）。这是迁移者反馈中最容易被忽略的一条（"you should strictly follow the example implementations in the repo"）。
5. **如果你短期不打算迁移**：至少把 (a) `navigator.storage.persist()` 在 Android 上主动调用一次（官方文档说 Android 可用），(b) 加上问题 1 第 4 条的"回前台健康检查 + 写入返回值校验 + Preferences 副本 + JSON 导出"。这能在不重写存储层的前提下把风险从"高"降到"中"。

## 3. 移动端 WebView 应用的调试方式

### 结论

1. **Android + Chrome DevTools 是最顺畅的一条路**，Ionic 官方有完整步骤文档；前提是设备开启开发者模式 + USB 调试。Capacitor 的 release 构建默认关闭 WebView 调试，**debug 构建才可被 `chrome://inspect` 发现**（社区 PR 的实践，见证据 D）。
2. **iOS + Safari Web Inspector 可调试 WKWebView，但有一个关键前提：必须是 developer provisioned 的 App，且从 iOS 16.4 起需要 `isInspectable`。** WebKit 官方文档写明可调试对象包括"web content that is configured to be inspectable in **developer provisioned** apps"；`docs.inspect.dev` 更直接写明 Inspect 工具"can only debug web content in **developer provisioned applications** or applications with the `com.apple.webinspector.allow` entitlement"，并点名 iOS 16.4 的 `isInspectable` 属性。**这意味着你日常用 Xcode 直接装到真机/模拟器的 debug 包可以调，TestFlight/App Store 正式包通常不行。**
3. **iOS 模拟器的远程检查是默认开启的**（WebKit 官方原文），无需在设备上开 Web Inspector 开关——但模拟器不等价真机（无法复现问题 1 的后台内存压力场景）。
4. **纯手机端（不连电脑）的应用内调试工具**：`eruda` 与 `vConsole` 都可用，且 eruda 维护更活跃（eruda 3.4.3，2025-06 发布，月下载 40.5 万；vConsole 3.15.1，2023-06 发布，月下载 31.2 万）。**TanStack Query Devtools 与 React DevTools 的"移动端可用性"本次未能取得官方明确支持声明**，列入未查证（但注意：你的课程表用 Dexie，`TanStack Query Devtools` 与 Dexie 无直接关系，若用 Dexie liveQuery 则不适用）。
5. **Capacitor 官方有内置 live reload**，并且**官方明确要求真机与电脑在同一 Wi-Fi**；文档同时给了 Ionic CLI（`ionic cap run ios -l --external`）和裸 CLI（`npx cap run --live-reload --port 8100` / `server.url` in `capacitor.config.json`）两条路径。

## 4. 手机端"看效果"的低成本方案

### 结论

1. **完全可以在不打原生包的前提下逼近原生表现，但必须用 PWA 独立窗口模式，且 `display` 必须是 `standalone` 或 `fullscreen`。** 这一点有 WebKit 官方的一手证据（#232302 的官方回复）——不只是"更好看"，而是**直接决定了 iOS 上的数据是否受 7 天清理影响**。所以这不只是"看效果"的问题，也是持久化策略的一部分。
2. **`viewport-fit=cover` + `env(safe-area-inset-*)` 是必需项，不是可选项。** MDN 明确 `env()` 自 2020-01 起全平台基线可用；同时 MDN 也给出了 `safe-area-max-inset-*` 这一组"静态最大值"变量，用于在动态 UI 收缩时保持布局不动——**这正好解决课表这类密集布局最怕的"行高跳动"问题**。
3. **`100vh` 在 iOS 上是已知的坑，`dvh` 是正解，但要留意历史实现差异。** WebKit Bugzilla #261185（`svh`/`dvh` 在 Safari 标签栏隐藏时意外相等）已被 **RESOLVED FIXED**，提交 `270516@main` / `270652@main`（2023-11）。**注意：该 bug 是关于 Safari 的标签栏，而你在 PWA 独立窗口 / Capacitor WebView 里没有 Safari 标签栏动态收缩这回事**——所以对"打包后"的场景，`100vh` 的坑比 Safari 网页里小得多。
4. **`position: sticky` 在 iOS 上的滚动容器行为确有问题报告，但需要谨慎对待证据强度。** WebKit #317443 报告了 `position:sticky/fixed` + `border-radius` + `overflow:clip` + `box-shadow` 组合导致 3 秒级滚动冻结（iOS 26.5.1），但 **WebKit 工程师无法复现，最终 RESOLVED INVALID**。→ **可以作为"要避免的 CSS 组合"的经验参考，但不能当作已确认的平台 bug 写进技术决策。**
5. **iOS Safari 与 Android Chrome 在独立窗口模式下的确切差异清单，本次只查证到部分**（`display` 模式要求、safe-area、dvh）。**"地址栏隐藏、状态栏区域、触摸滚动惯性"的逐项对比未取得官方文档级证据**，列入未查证。

### 证据与出处

**A. `display: standalone` 对 iOS 行为的决定性作用（WebKit Bugzilla #232302，John Wilander）** — <https://bugs.webkit.org/show_bug.cgi?id=232302>

原始报告（逐字）：

> "Our `manifest.json` file has `"display"` set to **`"minimal-ui"`**, so the PWA displays in Safari instead of its own window. Could this be the case of the data loss?"

官方回复（逐字）：

> "If you adjust your manifest to use either the **"standalone" or "fullscreen"** display mode, your home screen web application will **open full-screen in Web.app and you will get the behavior you want**."

**B. `env()` 与 safe-area 变量（MDN）** — <https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/env>

- Baseline：「This feature is well established… available across browsers since **January 2020**」
- 变量清单（逐字）：
  > "`safe-area-inset-top`, `safe-area-inset-right`, `safe-area-inset-bottom`, `safe-area-inset-left` — The safe distance from the top, right, bottom, or left inset edge of the viewport… The values are `0` if the viewport is a rectangle and no features — such as toolbars or dynamic keyboards — are occupying viewport space; otherwise, it is a `px` value greater than `0`."
  > "`safe-area-max-inset-top`, … — The **static maximum values** of their dynamic `safe-area-inset-*` variable counterparts **when all dynamic user interface features are retracted**. While the `safe-area-inset-*` values change as the currently-visible content area changes, the **`safe-area-max-inset-*` values are constants**."
  > 另有 `keyboard-inset-*`（虚拟键盘尺寸，VirtualKeyboard API）与 `viewport-segment-*`（折叠屏设备）。

**C. `dvh` / `svh` 在 iOS 的历史 bug（WebKit Bugzilla #261185，RESOLVED FIXED）** — <https://bugs.webkit.org/show_bug.cgi?id=261185>

报告（逐字）：

> "Mobile Safari is **not distinguishing between the CSS units `svh` and `dvh`**. These units should yield different dimensions in certain circumstances, however, instead they are yielding the same dimensions in all circumstances… Captured on an iPhone running **iOS 16.4.1**."

WebKit 工程师 Abrar Rahman Protyasha（逐字）：

> "I agree that this is unexpected behavior. Our **small viewport units are not spec compliant currently** because we allow clients to override layout parameters without enforcing collection of the minimum unobscured layout size…"
> 修复提交：`Committed 270516@main (cc2d17a95691)` 与 `Committed 270652@main (43148740f3be)`（2023-11-10 / 2023-11-13）。

**D. `position: sticky` + `overflow: clip` + `box-shadow` iOS 滚动卡顿报告（WebKit Bugzilla #317443，RESOLVED INVALID）** — <https://bugs.webkit.org/show_bug.cgi?id=317443>

报告（逐字）：

> "When combining the following CSS properties on a sticky or fixed positioned element, **scroll performance on iOS Safari degrades severely — dropping to 1-6 FPS with 3000-3400ms frame delays during scroll**… **Removing any one of `border-radius`, `overflow:clip`, or `box-shadow` from `.pill` resolves the issue.** … Tested on: iPhone, **iOS 26.5.1**… **Not reproducible on: Chrome desktop, Brave, Arc**."
> WebKit 工程师 Said Abou-Hallawa（逐字）："**I cannot reproduce this bug using the above test case.**"
> Alexey Proskuryakov（逐字）："I also cannot reproduce any scrolling issues on this test. **Marking as resolved for now**…"

**E. MDN 存储容量（与移动端看效果/限制相关）** — <https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria>
  → localStorage 5 MiB/origin、Web Storage 总计 10 MiB 上限。见问题 1 证据 E。

**F. Capacitor Live Reload（真机场景，与"低成本看效果"直接相关）** — <https://capacitorjs.com/docs/guides/live-reload>
  → 见问题 3 证据 E：**必须同一 Wi-Fi**；server 必须绑 `0.0.0.0`；`server.url` + `cleartext: true`；`npx cap run --live-reload --port 8100`。

### 对本项目的建议

**分三档，成本递增：**

**第 1 档（零成本，今天就能做）——把 PWA 当"准原生"用：**

```html
<!-- index.html -->
<meta name="viewport"
      content="width=device-width, initial-scale=1, viewport-fit=cover" />
```
```json
// manifest.webmanifest —— 这一条直接关系到 iOS 上数据是否受 7 天清理影响
{
  "display": "standalone",     // 不要用 minimal-ui / browser
  "display_override": ["standalone"],
  "orientation": "portrait"
}
```
```css
:root {
  /* 密集课表布局：用 max-inset 做"恒定预留"，避免动态 UI 收缩时行高跳动 */
  --safe-top:    env(safe-area-inset-top, 0px);
  --safe-bottom: env(safe-area-inset-bottom, 0px);
  --safe-left:   env(safe-area-inset-left, 0px);
  --safe-right:  env(safe-area-inset-right, 0px);

  /* 课表容器高度：优先 dvh，回退 svh/vh */
  --viewport-h: 100vh;
}
@supports (height: 100dvh) { :root { --viewport-h: 100dvh; } }

.timetable-shell {
  height: var(--viewport-h);
  padding-top: var(--safe-top);
  padding-bottom: var(--safe-bottom);
  padding-left: var(--safe-left);
  padding-right: var(--safe-right);
  overflow-y: auto;              /* 单一滚动容器 */
  -webkit-overflow-scrolling: touch;
}
```
iOS 加到主屏后就是独立的 `display-mode: standalone` 窗口，**没有地址栏、没有 Safari 标签栏** —— 这已经非常接近原生观感，而且此时的 safe-area 才真正非零（在 Safari 标签页里经常是 0，容易误以为"没问题"）。

**第 2 档（低成本）——用 live reload 在真机上看真实渲染：**
`npx cap run ios --live-reload --port 8100`（前提：手机与电脑同一 Wi-Fi）。这比反复 `npm run build && npx cap sync && Xcode Run` 快一个数量级，但**仍然需要打一次原生包**，所以它不解决"完全不想打原生包"的诉求。若要严格零原生包，用第 1 档 + 手机浏览器"添加到主屏幕"。

**第 3 档（课表密集布局的专项防御）：**
- **显式声明滚动容器，别依赖 body 滚动。** 课表是"固定表头 + 可滚网格"，请让 `.timetable-shell` 成为唯一的 `overflow-y: auto` 元素，并配合 `position: sticky` 表头。**在有明确滚动容器的场景下，sticky 的行为在 iOS/Android 上都更可预测**（这也是 WebKit 工程师在 #317443 复现失败所暗示的方向）。
- **避开 #317443 报告中的 CSS 组合**：`position: sticky`/`fixed` 的卡片上**不要同时**叠加 `border-radius` + `overflow: clip` + `box-shadow`。报告虽被判定 INVALID，但这是零成本的规避——课表格子用纯色边框替代阴影即可。**注意 `overflow: clip` 尤其危险，因为很多"圆角裁剪"写法会顺手加上它。**
- **`100vh` 只在无法用 `dvh` 时回退**，并用 `@supports` 分层。历史 bug（#261185）已在 2023-11 修复，但线上仍有旧 iOS（16.x）设备，回退链能兜住。
- **测试矩阵最小集**：iOS Safari 标签页 / iOS 主屏独立窗口 / Android Chrome 标签页 / Android Chrome 独立窗口。**这四种的 safe-area 和视口高度表现都不同**，前两种差异尤其大。用 `<meta name="theme-color">` 与 `display-mode` 媒体查询区分调试。
