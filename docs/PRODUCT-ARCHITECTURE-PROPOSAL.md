# 几微 2.0 产品与插件化架构提案

> 状态：方向已确认（2026-10-01）。本文是产品与架构边界说明；只有已标注“当前状态”的内容代表已经实现，M2–M8 仍按路线逐步交付。
>
> 编制日期：2026-10-01（Asia/Shanghai）

## 1. 提案摘要

几微适合从“课程表应用”扩展为“围绕一个大学生学期的本地优先工作台”。课表仍然是入口，扩展方向只回答四类问题：

1. **我什么时候要去哪里？** 课程、日程、考试和地点。
2. **我接下来要完成什么？** 作业、截止日期、考试准备和轻量计划。
3. **我在这门课学到了什么？** 课程笔记、资料索引和复习回顾。
4. **我怎样把自己的数据带走或与可信的人协作？** 备份、标准格式导出、可撤销的分享和可选同步。

产品应继续把“本地、离线、无广告、不索要教务账号密码”作为默认承诺。云同步、持续日历订阅、班级协作和 AI 等能力可以成为明确的增值服务，但不能让本地核心失效，也不能把数据采集变成商业模式。

## 2. 对现有商业化分析的修正

`docs/产品分析.md` 对用户痛点和红线的判断很有价值，但其中有三处需要在实施前校准：

| 原判断 | 提案中的修正 | 影响 |
| --- | --- | --- |
| iCal 订阅成本低，能顺手解决跨设备 | 本地生成 `.ics` 文件是低成本；**长期订阅 URL**需要可持续的托管、更新、撤销和隐私保护 | M3 先交付文件导出与本地分享；托管订阅放到有明确服务成本和权限模型的阶段 |
| iCal 能解决“电脑和手机数据不通” | 它只能把已发布的事件送入日历，不能把用户在另一台设备的编辑同步回几微 | 不把日历订阅宣传成同步；同步仍属于 M8+ 的独立能力 |
| 云能力适合买断 | 服务器、存储、推送和带宽是持续成本；买断只适合有限期限或自托管导出 | 云同步与持续订阅采用成本透明的可选方案，必要时提供导出和删除入口 |

iCalendar 是标准的交换格式，支持事件、待办、日志和提醒等对象；重复课的停课例外可以用 `EXDATE` 表达。系统日历通常把 URL 订阅视为只读外部日历，因此“订阅”与“回写同步”必须分开描述。[RFC 5545](https://www.rfc-editor.org/rfc/rfc5545)；[Apple 外部日历订阅说明](https://support.apple.com/guide/iphone/iph3d1110d4/ios)

## 3. 产品边界与目标用户

### 3.1 目标用户

- 想要干净、可靠、少打扰工具的本科生和研究生。
- 需要处理单双周、多校区、临时调课、考试与作业截止日的人。
- 愿意手动录入或从其他应用导出文件，不愿交出教务账号密码的人。
- 需要把课表、任务和笔记放在同一个学期语境中，但不想使用臃肿通用效率工具的人。

### 3.2 明确不服务的方向

- 校园匿名社区、信息流、二手市场、兼职和 O2O 导流。
- 任何索要教务系统密码、自动化模拟登录或未经授权抓取的导入方式。
- 广告 SDK、设备指纹、默认开启的行为追踪和出售用户数据。
- 以“AI”作为首页中心的聊天入口。AI 只能在用户主动提供内容后做本地或明确授权的辅助。

### 3.3 产品承诺

| 承诺 | 验收方式 |
| --- | --- |
| 没网仍能看、改和导出本地数据 | 浏览器离线、原生离线和恢复测试 |
| 核心功能无账号、无广告 | 首次启动和网络断开时均可使用 |
| 数据可带走 | JSON 全量备份、标准 CSV/ICS/Markdown 导出可回读 |
| 每一次上课时间有唯一真相 | 所有模块复用 `packages/core` 的展开与时区函数 |
| 插件权限可见、可撤销 | 安装前权限清单、运行时能力降级、卸载清理 |

### 4.1 推荐的用户主流程

```text
导入或快速录入课程
        ↓
今天/下一节课 + 系统日历
        ↓
考试与截止日 → 任务 → 课程笔记
        ↓
学期结束：导出备份、ICS、Markdown
        ↓
需要时再选择同步、分享或原生能力
```

这条流程让高频功能（任务、笔记、复习）围绕已有的课程语境增长，同时不把社区和无关内容塞进首页。

## 5. 插件化分层方案

“插件化”不应一开始就等同于“任意网页代码可以运行”。建议分三层逐步开放：

### L0：内置功能模块（现在可做）

继续使用当前 `FeatureModule` 注册表。`timetable`、`calendar`、`tasks`、`notes` 都是独立 feature，外壳只读取 `id/title/icon/order/render/widgets/setup`。模块之间不直接 import，跨模块通过 core 类型、只读查询和事件总线协作。

### L1：受控扩展包（M4–M7 期间验证）

扩展包以版本化 manifest 描述，不允许执行任意远程 JavaScript：

```ts
interface ExtensionManifest {
  id: string                 // 反向域名或 npm 风格命名空间
  version: string            // SemVer
  apiVersion: 1
  name: string
  permissions: Array<'read:blocks' | 'read:occurrences' | 'write:blocks' | 'write:notes' | 'notifications' | 'files'>
  contributes: Array<'module' | 'widget' | 'parser' | 'exporter' | 'theme'>
  dataNamespace: string
  entry: string              // 仅指向本地打包资源或经审核的扩展包
}
```

安装流程：查看 manifest 与权限 → 用户确认 → 校验签名/哈希 → 解压到本地扩展目录 → 运行迁移 → 显示可撤销权限。卸载时运行反向迁移并清理该 `dataNamespace`，核心数据不被删除。

### L2：沙箱插件（有真实生态需求后再做）

第三方插件只能通过窄 API 访问数据和能力，默认无网络、无 DOM、无任意文件路径访问。Web 端可考虑 Worker/受限 iframe，原生端使用独立 JS runtime 或 Capacitor bridge；不能把 `iframe` 当成完整安全边界。若使用 iframe，必须采用独立 origin、严格 CSP 和 sandbox，避免同时授予可逃逸的脚本与同源权限。[MDN iframe sandbox 说明](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe)

建议第一批插件类型仅开放：

- `parser`：把用户选定的 CSV/竞品导出文件转换成标准 `BlockDraft`；
- `exporter`：输出 Markdown、ICS 或图片；
- `widget`：只读展示课程、任务或笔记摘要；
- `theme`：只提供 CSS 变量，不接触数据。

暂不开放任意后台任务、网络抓取、教务登录、全库写入、支付和账号权限。这样能把插件生态的价值放在“转换和展示”，不会绕过产品红线。

### 6.1 与当前仓库的对应关系

| 提案层 | 当前对应 | 需要确认后再做的变化 |
| --- | --- | --- |
| Shell | `apps/web/src/App.tsx`、`modules.ts`、`JiweiContext.tsx` | 增加模块生命周期、错误边界、首页 widget 编排；先不引入重量级路由 |
| Feature | `apps/web/src/features/timetable` | 新模块各自目录；禁止互相导入 |
| Core | `packages/core` | 保持纯函数；补日期、时区、重复和冲突测试 |
| Data | `packages/data` | 先完善恢复事务和引用校验；以后再拆 engine/application |
| UI | `packages/ui` | 把 TimeGrid、WidgetCard、权限提示做成真正通用组件 |
| Platform | `packages/platform` | 继续通过 capability；原生能力只在 M5 实装后标记可用 |
| Plugin | 当前没有独立包 | 新增 `packages/plugin`，先只放契约、权限与本地内置扩展，不接第三方市场 |

### 6.2 关键数据与事件

- `Block` 仍是课程、日程、任务和考试共享的时间实体；`Occurrence` 仍是提醒、笔记和冲突的锚点。
- `PluginData`（建议新增）按 `extensionId + dataNamespace + key` 隔离，插件不能把自定义字段写入核心表。
- 业务写入通过 application use case 完成：`importBlocks`、`moveOccurrence`、`completeTask`、`attachNote`；插件拿不到 Dexie 实例。
- 事件总线只发布领域事件，如 `block.created`、`occurrence.materialized`、`task.completed`、`backup.restored`。事件载荷使用 core 类型，禁止传递数据库对象。
- `refresh()` 仍只更新读取信号；恢复和批量写入必须在事务成功后发布一次事件并同步选中学期状态。

## 7. 已确认的 M2–M8 重排

用户已确认按此方向推进；正式阶段定义已写入 `docs/ROADMAP.md`，代码仍按阶段逐步实现：

| 阶段 | 建议交付 | 退出条件 |
| --- | --- | --- |
| M2 | PWA 安装引导、离线/存储可靠性、字号密度、恢复后状态同步 | 手机主屏幕与飞行模式验收；P1 恢复问题有回归测试 |
| M3 | JSON/CSV/竞品导出导入、预览合并、`.ics` 文件导出 | 导入失败不改旧库；ICS 在至少一种桌面和一种手机日历中可读 |
| M4 | 日程/考试模块 + 首个内置模块模板 + 时间线首页 | `event/exam` 与课程共用 core 时间计算；不重复造日期逻辑 |
| M5 | 提醒规则、应用内降级、Capacitor 本地通知 | Web 文案不承诺锁屏闹钟；原生真机验证权限、杀进程、时区和电池策略 |
| M6 | 任务模块、截止日期、课程归属、首页 widget | 任务和课程冲突可解释；离线完成与恢复可用 |
| M7 | 课程笔记、Markdown/附件导出、搜索、插件 L1 只读 API | 笔记引用不因 occurrence 重建失联；插件不能越权写核心表 |
| M8 | 先做分享/同步技术验证，再决定服务化 | 有数据删除、导出、冲突、成本和隐私说明；未满足则保持本地优先 |

### M8 的商业闸门

只有同时满足以下条件，才进入云同步或班级协作：

1. 真实访谈/反馈中有重复出现的跨设备或协作需求；
2. 已能说明每个账号、设备、存储和推送成本；
3. 用户能随时导出、删除和停止同步；
4. 本地核心在服务器不可用时仍可读写；
5. 付费购买的是持续服务，不是把原有的离线功能锁起来。

## 8. 已确认的产品边界

1. **插件层级**：先做 L0 内置模块，M7 再验证 L1 受控扩展，暂不做任意第三方远程代码。
2. **功能优先级**：导入/备份与 ICS 先于日程、任务、笔记；不把云同步提前到 M3。
3. **商业边界**：本地核心永久免费、无广告；只对持续成本明确的同步、托管订阅或协作收费。
4. **AI 边界**：默认关闭，优先本地或逐次同意；不把课程内容或笔记默认上传。
5. **推进方式**：先把“今天”和课程表做成稳定可用的应用，其他模块先提供入口和空状态，再逐阶段实现。

## 9. 当前未完成与验证边界

- M2–M8 路线已写入 `docs/ROADMAP.md`；本轮只完成“今天”首页、离线/安装提示和平台适配插座，未提前实现记账、笔记、待办或 AI 业务。
- 交接文档列出的恢复回滚、恢复后选中学期、周数边界、时钟刷新、调课跨度和日期时区问题仍然存在。
- 现有仓库有静态 `FeatureModule` 契约，但没有第三方插件安装、签名、沙箱、权限撤销或插件数据迁移实现。
- 原生通知的精确闹钟权限、系统限制和降级策略必须在 M5 真机验证。Capacitor 文档明确指出 Android 14 的 exact alarm 权限可能被关闭，关闭后精确通知可能被删除或降级。[Capacitor Local Notifications](https://capacitorjs.com/docs/apis/local-notifications)

## 10. 用户补充需求后的产品修订（2026-10-01）

以下内容覆盖前文同名功能的优先级描述，作为下一轮确认稿：

### 10.1 新的产品组合

| 模块 | 必须解决的场景 | 第一版边界 | 备注 |
| --- | --- | --- | --- |
| 课程表导入 | 不想逐门录入课程 | 图片识别课程表 + CSV/JSON/竞品导出文件；全部先进入预览和人工确认 | AI 只生成草稿，不直接写入正式课表 |
| 记账 | 快速记录支出和收入 | 金额、收支方向、分类、商户、日期、备注、附件、月度汇总 | 本地数据优先；发票/小票图片属于敏感数据 |
| AI 识图记账 | 拍小票后少填字段 | OCR → 金额/日期/商户/明细候选 → 用户确认 | 识别失败必须能手动修正；不承诺财务或报税准确性 |
| 手写笔记 | 课堂上直接写 | 笔画、橡皮、撤销、页面和图片附件；可导出原图/PDF | 先做手写画布，不把手写识别当成前置条件 |
| 文字记录 | 随手记下想法和课堂内容 | Markdown/纯文本、标签、课程/课次关联、搜索 | 手写与文字可放在同一条笔记中 |
| 待办 | 知道下一件要完成的事 | 标题、截止日期、优先级、课程关联、完成状态 | 后续再做子任务和重复规则 |
| 今日总览 | 一眼看到今天的生活学习负担 | 今日课程、待办、支出/收入、考试/日程、快速添加入口 | 只做聚合视图，不复制各模块数据 |
| AI 小助手 | 用一句话添加事项 | 识别“记一笔支出/加待办/记日程/写笔记/导入课程”意图并生成草稿 | 涉及写入、图片或联网的动作必须二次确认 |

推荐的首批官方模块为：`timetable`、`ledger`、`notes`、`tasks`、`agenda`、`assistant`。官方模块按需启用；开发者插件延后到受控扩展 API 稳定后开放。

### 10.2 AI 与识图的安全工作流

```text
用户输入文字/图片
        ↓
本地 OCR 或用户明确同意的云端 OCR
        ↓
结构化草稿（字段 + 置信度 + 原图引用）
        ↓
用户预览、修改、确认
        ↓
application use case 写入核心仓储
        ↓
发布领域事件并刷新今日总览
```

助手不能直接调用 Dexie、不能绕过表单校验、不能默认上传图片，也不能以聊天回复代替写入成功。每次执行都应生成可撤销的命令记录。课程表图片和小票识别要共享 `OcrAdapter`，但使用不同的领域解析器：`CourseTableParser` 输出 `BlockDraft[]`，`ReceiptParser` 输出 `TransactionDraft`。

原生端可优先使用设备端文字识别能力；Apple Vision 明确支持在设备上进行多语言文本识别，Google ML Kit 也提供设备端文字识别 API，这有利于离线和隐私，但中文课程表、手写字和复杂小票仍需用真实样本验证，不应把“有 OCR API”写成“识别一定准确”。[Apple Vision](https://developer.apple.com/documentation/vision/recognizing-text-in-images)；[Google ML Kit](https://developers.google.cn/ml-kit/migration?hl=en)

### 10.3 建议新增的领域模型

不立即改代码，先冻结语义：

```ts
Transaction {
  id, type: 'income' | 'expense', amount: string, currency,
  occurredAt, category, merchant?, note?, attachmentIds[], source,
  createdAt, updatedAt
}

NotePage {
  id, noteId, kind: 'text' | 'ink' | 'mixed',
  text?, strokes?, imageIds[], order
}

AssistantDraft {
  id, intent: 'courseImport' | 'transaction' | 'task' | 'event' | 'note',
  inputRefs[], fields, confidence, status: 'draft' | 'confirmed' | 'rejected'
}
```

金额用十进制字符串或最小货币单位保存，避免 JavaScript 浮点误差。图片与手写笔画放在附件/内容仓储，核心表只保留引用和元数据。`Transaction`、`NotePage` 和 `AssistantDraft` 都必须参与 JSON 备份与删除恢复测试。

## 11. 完全月租制与替代方案分析

### 11.1 完全月租制为什么有合理性

完全月租适用于持续产生成本的能力：云端 AI 识图、跨设备同步、托管 ICS、推送、协作和客服。它能带来可预测收入，使服务端存储、模型调用和持续维护有预算；多月订阅还能降低每次续费的操作成本。Apple 和 Google 都提供自动续订订阅机制，但商店服务费会直接减少开发者所得；Apple 文档说明通常首年按 70% proceeds 计算，小型开发者计划或续订满一年后可到 85%，Google Play 当前文档对自动续订订阅列出 15% 服务费。[Apple 订阅](https://developer.apple.com/app-store/subscriptions/)；[Google Play 服务费](https://support.google.com/googleplay/android-developer/answer/112622)

### 11.2 对几微的主要问题

| 风险 | 为什么对几微更明显 | 结果 |
| --- | --- | --- |
| 使用季节性 | 课程表在开学前后最常用；考试、记账和笔记可能持续，但未验证 | 月租容易在假期被取消 |
| 价值与成本错配 | 本地课程表、手写、文字笔记和基础记账没有持续服务器成本 | 为本地能力强制月租会违背“本地优先、干净免费”的信任基础 |
| 学生支付阻力 | 学生会比较通用日历、备忘录、记账 App 和免费 OCR | 首次转化、续费和口碑压力都高 |
| 订阅疲劳 | 用户已有多个影音、学习和效率订阅 | 需要持续解释“本月为什么值得续费” |
| 平台复杂度 | PWA、App Store、Google Play 的购买、恢复购买和跨端权益不同 | 账号、支付和客服工作会提前挤占产品开发 |
| AI 成本波动 | 图片大小、模型和重试次数会让单用户成本不稳定 | 不能无限量承诺 AI 识图；需要公平使用策略 |

结论：**完全月租可以作为云增强版的商业模式，但不适合作为整个几微的唯一入口，也不应锁住本地课程表、待办、笔记和基础记账。**“多月一订”比纯月租更适合学期型产品，但必须允许暂停、取消、导出和降级到本地模式。

### 11.3 推荐的替代方案

| 方案 | 用户购买什么 | 好处 | 代价/限制 | 推荐度 |
| --- | --- | --- | --- | --- |
| 本地永久免费 + 云增强月租 | 同步、云端 OCR、AI 助手、托管 ICS、分享 | 保留信任；收入与持续成本对应；低门槛试用 | 需要清楚区分本地与云端状态 | **最高** |
| 学期通行证 | 一学期的同步、AI 识图额度和协作 | 与大学生支付节奏一致；假期无需续费 | 收入不如全年订阅平滑 | **很高** |
| 年付/多月折扣 | 连续服务打包，按月均价降低 | 降低流失和支付摩擦；适合高频笔记与记账用户 | 退款、公平使用和学期中途购买要设计好 | 高 |
| AI 按量包 + 本地功能免费 | 只购买云端 OCR/总结次数 | 成本透明；不必为不使用 AI 的用户收费 | 需要防止“次数限制”引发反感；本地 OCR 能力要先做好 | 高 |
| 原生能力一次性买断 | 原生包、系统通知、桌面小组件等 | 适合不想订阅的用户；价值容易解释 | 无法单独覆盖服务器和 AI 持续成本 | 中 |
| 班级/社团版 | 共享课表、只读日程、集体通知 | 付款方明确，客单价可能高于个人 | 需要权限、隐私、管理员和协作模型 | M8+ |
| 自托管/自带 Key | 用户自己承担服务器或模型费用 | 适合技术用户和开源社区，降低平台成本 | 普通学生配置门槛高；不能作为默认路径 | M8+ |

### 11.4 推荐的商业组合

```text
免费本地版
  课程表 / 导入导出 / 今日总览 / 待办 / 手写与文字笔记 / 基础记账
  本地 OCR（平台支持时）/ 完整备份 / 无广告 / 无账号

可选学期通行证或月租
  多设备同步 / 云端 OCR / AI 小助手云端能力 / 托管 ICS / 分享与协作
  透明的用量、到期后降级策略、导出与删除

按量增值
  高成本的云端识图、长文总结、批量导入；默认不自动续费
```

建议先用访谈和小范围灰度测试比较“月租、学期通行证、按量包”三种支付意愿，不在没有真实留存和 AI 成本数据时承诺最终价格。若必须先选一个方向，我建议：**本地永久免费 + 学期通行证为主 + 月租作为补充 + AI 按量包作为成本保护**。

### 11.5 对 M2–M8 的产品影响（已写入正式路线图）

| 阶段 | 新增重点 | 原因 |

## 12. 架构就绪度审计：模块开关与 AI

### 12.1 当前结论

当前架构**部分具备基础，但还不能承诺未来所有功能都已经插件化**。

已经存在的基础：

- `apps/web/src/modules.ts` 有静态 `FeatureModule` 注册表，外壳通过模块渲染页面；新增官方模块不需要把业务代码塞回 `App.tsx`。
- `packages/ui/src/module.ts` 已有 `id/title/icon/order/render/widgets/setup` 契约，适合先承载官方模块和首页卡片。
- `Block + Occurrence` 可以统一承载课程、日程、任务、考试，`Note`、`Alert` 已预留关联点。
- `packages/data` 的仓储接口和 `packages/platform` 的能力适配层为存储、文件、通知和原生能力隔离了实现细节。

仍然缺少的闭环：

- 没有持久化的模块启用状态、依赖检查、版本迁移和禁用后的数据处理策略。
- `setup` 当前没有稳定的 `AppContext`，模块仍可能直接组合仓储调用，缺少统一的应用用例和领域事件边界。
- 没有第三方扩展的 manifest、权限、签名/哈希校验、安装卸载、沙箱和数据命名空间实现。
- 没有 AI provider、结构化意图、工具调用、用户确认、审计记录和用量控制。

因此，提案中的插件化和 AI 设计属于**下一步要落地的架构增量**，不是当前仓库已经完成的功能。

### 12.2 官方模块开关的落地方案

建议把现有 `FeatureModule` 扩展为 manifest + runtime 两部分：

```ts
interface ModuleManifest {
  id: string
  version: string
  kind: 'official' | 'extension'
  title: string
  defaultEnabled: boolean
  dependencies?: string[]
  permissions: Permission[]
  dataNamespace: string
  contributes: Array<'page' | 'widget' | 'parser' | 'exporter' | 'assistantTool'>
}

interface ModuleRuntime {
  manifest: ModuleManifest
  render: ComponentType
  widgets?: WidgetDef[]
  setup?(ctx: AppContext): void | Promise<void>
  teardown?(ctx: AppContext): void | Promise<void>
}
```

新增 `ModuleManager`，职责固定为：

1. 读取模块注册表和 `Meta` 中的 `module:<id>` 设置；
2. 校验依赖、版本和平台能力；
3. 启用时执行迁移和 `setup`，禁用时执行 `teardown`；
4. 只把已启用模块交给导航和首页 widget；
5. 卸载扩展时按 `dataNamespace` 清理扩展数据，核心课程、账目和笔记必须由用户另行确认；
6. 对缺失依赖、迁移失败和权限拒绝给出可恢复错误。

模块开关的用户语义要分成三种：

| 操作 | 行为 |
| --- | --- |
| 隐藏 | 保留数据和设置，不显示导航/widget |
| 停用 | 停止后台任务和通知，保留数据，之后可重新启用 |
| 卸载扩展 | 删除扩展代码；先导出或确认清理扩展专属数据 |

官方模块可以静态打包、按需启用；第三方插件必须经过 manifest、权限和版本检查。这样既满足功能开关，也避免把“隐藏页面”误称为“安全插件系统”。

### 12.3 AI 的明确架构

AI 不直接写数据库，而是一个位于 `application` 层的“草稿生成器 + 受控工具调用器”：

```text
输入：文字 / 图片 / 当前页面上下文
                ↓
InputNormalizer（裁剪、压缩、脱敏、OCR）
                ↓
IntentRouter（识别任务类型）
                ↓
AiProvider（本地模型 / 云模型 / 无 AI 降级）
                ↓
Zod 结构化 Draft + 字段置信度 + 原始引用
                ↓
Preview / Edit / Confirm
                ↓
Application Use Case（唯一写入口）
                ↓
Repos 事务写入 + Domain Event + 可撤销记录
```

第一批固定意图，不允许模型自由生成数据库操作：

```ts
type AssistantIntent =
  | { type: 'courseImport'; draft: CourseImportDraft }
  | { type: 'createTransaction'; draft: TransactionDraft }
  | { type: 'createTask'; draft: TaskDraft }
  | { type: 'createEvent'; draft: EventDraft }
  | { type: 'createNote'; draft: NoteDraft }
```

每个意图对应一个白名单 use case，例如 `importCourses`、`createTransaction`、`createTask`。模型只负责提出结构化参数，use case 负责 schema 校验、权限检查、冲突检查、事务写入和撤销信息。

### 12.4 AI provider 与隐私策略

```ts
interface AiProvider {
  id: string
  capabilities: Array<'ocr' | 'courseParse' | 'receiptParse' | 'textAssist'>
  locality: 'device' | 'selfHosted' | 'cloud'
  analyze(input: AiInput, schema: StructuredOutputSchema): Promise<AiResult>
}
```

建议提供三种实现：

- `LocalProvider`：规则、设备端 OCR、可用时的本地模型；默认路径，支持离线。
- `CloudProvider`：用户逐次同意后上传必要图片/文字；显示供应商、字段、保留时间和用量。
- `NoAiProvider`：AI 不可用时回到手动表单、CSV/JSON 导入和普通文字输入。

OCR 与大模型分离：课程表和小票首先经过 `OcrAdapter`，结构化解析可以由规则/本地模型完成；复杂总结和自然语言改写才调用 LLM。这样可以控制成本，也能让敏感图片尽量留在设备上。

必须遵守以下规则：

- 默认关闭云端 AI，不把账单、课程表、笔记上传作为启用模块的隐含条件。
- 课程批量导入、财务记录、带图片的上传和批量修改始终需要用户确认。
- 识别结果显示置信度、原始图片或文本引用和可编辑字段。
- 每次 AI 写入产生可撤销命令；失败、超时和重复请求必须幂等。
- AI 用量由 `AiUsagePolicy` 统一管理，支持本地免费、学期额度、按量包和月租权益；插件不能自行保存平台 API Key。
- 不把模型回答作为事实来源；涉及金额、日期、课程时间和提醒时，以结构化数据校验结果为准。

### 12.5 插件与 AI 的关系

第三方插件只能通过受控 `assistantTool` 声明扩展 AI 能力，例如“把某种格式解析成课程草稿”。插件不能直接调用模型、读取全部笔记或写入账目；它必须申请最小权限，并返回版本化的结构化结果。官方 `assistant` 模块负责统一确认、计费、日志和隐私提示。

完成上述 `ModuleManager`、`AppContext`、`Application Use Case`、`AiProvider` 和 `AssistantDraft` 后，才可以说架构真正为“官方模块按需启用、未来开发者插件、AI 辅助写入”打好了基础。
