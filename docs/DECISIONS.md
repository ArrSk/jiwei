## ADR-010 · 官方模块按需启用与 AI 确认写入

**状态**：已确认（2026-10-01；按阶段实现）

### 背景

产品会从课表扩展到日程、待办、记账、笔记和 AI 助手。用户希望只打开需要的功能，同时要求 AI 识图和自然语言添加事项时可控、可解释。

### 决策

1. 官方功能先作为独立的 L0 内置模块注册；M4 起由本地偏好控制显示/隐藏，关闭模块不删除它的数据。
2. 开发者插件延后到 M8 的受控 L1；先有 manifest、权限清单、数据命名空间和卸载清理，不运行任意远程代码。
3. AI 统一走“输入 → 识别/解析 → 结构化草稿 → 用户预览确认 → use case 写入”的流程，不能直接访问 Dexie 或绕过表单校验。
4. 图片默认本地处理；使用云端 OCR/模型前逐次说明并征得同意。课程表识图和小票识图共用能力适配层，但使用不同领域解析器。
5. 本地课程表、待办、笔记和基础记账保持免费可用；持续产生服务器/模型成本的同步、云 AI 和托管服务另行评估。

### 后果

- 首页可以逐步接入各模块 widget，而不复制业务数据；模块间通过 core 类型、仓储和领域事件协作。
- AI 识别错误不会直接改动正式数据，但每次确认都需要清晰的草稿预览和失败反馈。
- M2–M8 先按 [`ROADMAP.md`](ROADMAP.md) 逐阶段交付，未实现的能力不在设置页标记为可用。


## ADR-001 · 产品定位与首个模块范围

**状态**：已确认

### 背景
最初需求是"课程表应用"，随后明确为：**面向大学生日常生活的 App，首版只做课表**，
后续会加入日程表、重要事件提醒、闹钟、笔记等**多个**功能。

### 决策
1. **产品定位**：大学生日常生活 App（长期目标），课表是**第一个模块**。
2. **首版（M1）只交付课表**：学期/作息管理、手动录入与表格编辑、周/日视图、今天卡片。
3. **不做账号系统**（单用户）、**不做教务系统抓取**（仅保留 parser 接口）。
4. **前端框架**：React 19 + Vite + TypeScript。
5. **架构必须支持后续模块"嵌入而非重构"**。

### 理由
- 单用户 → 不需要鉴权、租户、权限模型，M1 复杂度大幅下降，本地即可完整使用。
- 手动 + CSV/JSON 导入已覆盖真实需求；教务抓取收益低且随学校改版失效。
- 定位放宽后，"首版只有课表"与"以后加很多功能"之间的矛盾**必须靠架构解决**，这是 ADR-005 的直接动因。

### 后果
- **不做的**：注册登录、多租户、教务模拟登录、验证码、定时抓取任务。
- **保留的**：`@jiwei/core` 的模型与来源无关；将来加教务解析器时业务代码零改动。
- 备份策略：一键导出/导入 JSON（本地优先的关键保障）。

## ADR-002 · 本地优先，首版不做服务器

**状态**：已确认

### 背景
目标是"网页可访问 + 手机可用"的个人应用。服务器带来同步与推送，也带来部署、成本、可用性负担。

### 决策
**本地优先**：数据先写本地数据库，离线完整可用；**M1~M4 不部署任何服务端**。
服务器仅在两种需求出现时引入：① 多设备同步 ② Web Push 推送。

### 理由
- 单用户场景下，服务器是纯负担：要买/维护机器、要 HTTPS 域名、断网就不可用。
- 本地优先的 UX 更好：打开即用、无加载态、地铁里也能记笔记。
- 数据模型与仓储接口（`@jiwei/data`）与将来服务端保持一致的**语义契约** ⇒ 事后加同步不是重写，而是新增一个仓储实现。

### 后果
- **代价**：换设备/清浏览器数据会丢数据 → 用**一键导出 JSON 备份** + 申请持久化存储（`navigator.storage.persist()`）对冲；UI 要提示备份。
- **代价**：多设备同步需等到 M8+。
- **收益**：零运维、零成本、离线可用；`apps/api` 可以先只留目录不实现。
- **触发引入服务器的条件**（任一）：需要手机在应用关闭时收到提醒；需要在两台设备间同步；需要分享给同学。

## ADR-003 · 存储选型：首版 IndexedDB，但数据层可替换

**状态**：已确认（用户选择"先用简单的方案"）

### 背景
本地优先需要一个浏览器端持久化方案。候选：

| 方案 | 实现成本 | 查询能力 | 事务 | 全文搜索 | 与服务端同构 |
| --- | --- | --- | --- | --- | --- |
| localStorage | 最低 | 无（自己遍历） | 无 | 无 | ❌ |
| **IndexedDB + Dexie** | **低** | 索引可用，复杂查询要手写 | ✅ | ❌（需自己建索引） | ❌ |
| SQLite on Web (wa-sqlite/OPFS) | 中（+1MB WASM、OPFS 兼容处理） | 真 SQL | ✅ | ✅ FTS5 | ✅ |

### 决策
1. **首版用 `IndexedDB`（Dexie 封装）** 作为持久化引擎，优先把课表功能做出来。
2. **但数据访问必须经 `@jiwei/data` 的仓储接口**（`BlockRepo` / `SemesterRepo` / `OccurrenceRepo` / `AlertRepo` / `NoteRepo`），
   业务代码与 `features/*` **只依赖接口，不直接依赖 Dexie**。
3. **领域模型仍用 Zod 定义在 `@jiwei/core`**（与存储引擎解耦，将来换引擎不动模型）。
4. **迁移路径已确定**：当出现"复杂日期范围查询变多 / 笔记全文搜索 / 需要与服务端同构"时，
   把引擎换成 SQLite（wa-sqlite/OPFS），**只替换 `@jiwei/data` 的实现层**，上层零改动。

### 理由
- 用户的首要目标是"**先把课表做出来**"，IndexedDB 省掉 WASM 加载、OPFS 兼容与 Worker 边界三类成本。
- 课表数据量极小（一学期几百条），IndexedDB 的索引能力足够；"按日期范围 + kind 过滤"用 `[date+kind]` 复合索引可解。
- **风险点已用接口隔离**：IndexedDB 最大的问题是"迁移时要重写数据访问"，而这一条通过仓储接口被限制在单个包内。

### 后果
- **代价**：没有 SQL 事务语义 → 重建 `Occurrence` 需要**自己保证原子性**（做法：在单个 Dexie 事务里"先删后写"，失败则回滚）。
- **代价**：没有 FTS5 → M7 笔记搜索先用**内存倒排索引 + 分词**（数据量小够用），迁移 SQLite 后再换 FTS5。
- **代价**：**没有服务端同构** → 将来引入同步时，服务端用 Drizzle+SQLite，`@jiwei/data` 需要新增一个"远程仓储实现"（接口不变）。
- **收益**：M0/M1 更快落地，依赖更少，调试更简单。
- **触发迁移 SQLite 的条件**（任一）：① 需要跨模块复杂查询（日程 + 课表 + 任务混合排序）变得难写 ② 笔记全文搜索要求变高 ③ 数据量或查询复杂度让 IndexedDB 手写索引明显吃力 ④ 决定接服务端同步。

### 对冲措施（必须在 M1 就做）
1. **`@jiwei/data` 只暴露仓储接口**，`features/*` 里禁止出现 `import Dexie` —— 用 ESLint 规则强约束。
2. **一键导出/导入全量 JSON 备份**（M3），作为存储引擎更换与数据丢失的兜底。
3. **`Meta` 表记录 `storageEngine` 与 `schemaVersion`**，为将来迁移留出"检测 + 数据搬运"入口。

## ADR-007 · 存储实现与访问接口分离（配合 ADR-003）

**状态**：已确认

### 背景
ADR-003 选择了 IndexedDB，并明确将来可能迁移到 SQLite。若业务代码直接用 Dexie，
迁移即等于重构 —— 这正是上一轮"课程中心模型"犯过的同类错误（把实现细节写进了架构中心）。

### 决策
**仓储模式（Repository）+ 依赖倒置**：
- `@jiwei/data` 对外只导出**接口**（`SemesterRepo`、`BlockRepo`、`OccurrenceRepo`、`AlertRepo`、`NoteRepo`、`MetaRepo`）与一个 `createRepos(engine)` 工厂；
- 引擎实现放在 `packages/data/src/engines/{dexie, sqlite}/`；
- `@jiwei/core` 定义领域模型与纯函数，**不认识任何存储引擎**；
- 切换引擎 = 换一个 `createRepos` 的入参。

### 理由
- 让"以后可能换存储"从一个**重构风险**降级为一个**配置项**。
- 与 ADR-005（平台能力适配层）同构：**在实现周围画一条接口线，把未来的变化关进一个包**。
- 成本极低：几个 TypeScript `interface` + 一个工厂函数。

### 后果
- **代价**：多一层间接（`repos.blocks.listByRange()` 而不是 `db.blocks.where(...)`）；需要写少量映射代码（Dexie 文档 ↔ 领域模型）。
- **收益**：迁移 SQLite 或接入服务端同步时，改动被限制在 `packages/data/src/engines/` 内。
- **纪律**：`features/*` 中 `import Dexie` 属违规，由 ESLint `no-restricted-imports` 拦截。

## ADR-004 · `Block` + `Occurrence` 时间锚点模型

**状态**：已确认（第二轮评估后）

### 背景
原方案以 `Course`/`CourseSession` 为模型中心。评估"能否支撑日程/提醒/笔记"时发现：
日程表勉强能塞，**提醒与笔记实质不兼容**（只有"课"能提醒；笔记只能贴在课程上，且只有一段纯文本）。

### 决策
1. **`Block` 是唯一"占时间"的实体**，`kind ∈ {course, event, task, exam}`；课表只是 `kind='course'` 的**视图**。
2. **`anchor` 用判别联合**表达时间语义：`curriculum`（教学周×星期×节次，时刻由作息表派生）/ `absolute`（自带真实时刻）/ `allDay`。
3. **`Occurrence` 落库**，由 `@jiwei/core` 的 `materialize()` 幂等展开；**ID 确定性** = `${blockId}#${date}#${periodStart}`。
4. **`Alert` 统一闹钟与提醒**（只差 `mode` 与可用通道），用 `ownerType/ownerId` 挂到 occurrence/block/semester/note。
5. **`Note` 用 `ownerType` 支持四种粒度**：单次课 / 整门课 / 学期随笔 / 独立笔记。
6. `materialize()` 是**唯一**的时间真相来源，任何地方不得自行计算日期。

### 理由
- `CourseSession` 距通用日历事件只差 `kind`、时间规格、日期锚定三个字段——**现在补是加字段，以后补是拆表迁移**。
- 提醒服务的是"具体某一次"，与"是课还是日程"无关 ⇒ 只实现一次。
- 确定性 ID 是扩展性的地基：**重建实例后，挂在上面的闹钟和笔记永不丢失**。

### 后果
- **代价**：M1 多约 1 天（先把 TimeSpec / 展开逻辑想清楚）。
- **收益**：日程表 ≈ 加一个视图；提醒、闹钟、笔记各只写一次；iCal 导出与搜索只实现一次。
- **明确不做**：不引入 CalDAV 协议、不做双向日历同步（保留为后期选项；届时 `Block` 就是现成的映射源）。

## ADR-005 · 模块化外壳 + 平台能力适配层

**状态**：已确认（本轮）

### 背景
用户明确："**现在只想要课表一个功能，以后会加入很多新功能**"。这意味着"加功能时不能改课表"。

### 决策
1. **模块化外壳**：每个功能是一个自注册的 `FeatureModule`（id / title / icon / routes / widgets / setup）；
   `apps/web/src/modules.ts` 静态导入全部模块，外壳据此生成导航与首页 widget 网格。
2. **feature 之间禁止互相 import**：跨模块协作走 `@jiwei/core` 类型与 `@jiwei/data` 仓储。
3. **`packages/platform` 能力适配层**：暴露 `capabilities = { canAlarm, canBackgroundPush, canVibrate, canBadge, canFilesystem }`
   与 `notifications` / `alarm` / `storage` / `files` 接口；**业务代码禁止直接调用 Web API**（如 `new Notification()`）。
4. **首版就落地**这两者，即使 M1 只有一个模块。

### 理由
- 成本极低（一个约 20 行的注册表 + 一个外壳组件 + 一层薄封装），收益是"加模块不用碰旧代码"。
- 能力适配层是 [ALARM-STUDY.md](research/ALARM-STUDY.md) 的直接要求：闹钟必须走原生调度，
  若业务代码散落 Web API，将来接 Capacitor 要全量翻改。
- 这也是"**只通用化接口，不提前实现功能**"的落地方式：M1 不写任何闹钟/笔记逻辑，只把插座装好。

### 后果
- **代价**：多两个包与一层间接；模块契约需要一次设计（后续改动会波及所有模块）。
- **收益**：加模块 = 加目录 + 加一行注册；Web 与原生共用同一份业务代码。
- **纪律**：M1 的 `packages/platform` 里**不实现** alarm 通道（只定义接口与能力探测，Web 实现返回 `canAlarm:false`）。

## ADR-006 · Capacitor 原生外壳承载闹钟

**状态**：已确认（闹钟定位为"锦上添花"，排在 M5）

### 背景
用户要求的功能里包含"**闹钟**"。经论证（见 [ALARM-STUDY.md](research/ALARM-STUDY.md)）：
纯 Web/PWA **无法**在锁屏、应用不在前台时可靠响铃 —— 浏览器会冻结后台定时器，
Web Push 既无时序保证也无法"响铃/震动/绕过静音"，系统级闹钟 API 只对已安装原生应用开放。

### 决策
1. **Web 端永不承诺"必响闹钟"**：Web/PWA 的对应能力降级为"应用内提醒 + iCal 系统日历订阅"。
2. **原生能力通过 Capacitor 实现**：`apps/native` 是**壳工程**，复用 `apps/web` 的构建产物，
   用 `@capacitor/local-notifications` 做系统级调度（Android 走 `AlarmManager`）。
3. **不重写 UI**：不为移动端另建一套 RN/Flutter 工程（与"网页可访问"的目标冲突）。

### 理由
- 同一份代码同时产出 PWA 与原生包，是唯一能同时满足"网页能用 + 手机可用 + 有闹钟"的路径。
- 闹钟是"系统调度"能力，无法在 Web 层模拟，必须在架构上留出位置（ADR-005 的 `platform` 层）。
- 自用可只打 APK 侧载，无需应用商店开发者账号（上架才需要）。

### 后果
- **代价**：需要一个 Android Studio / Xcode 环境做打包；原生包需单独发版；iOS 的"静音下必响"需申请 Critical Alerts 权限（普通本地通知在静音/专注模式下可能不响，需在 UI 说明）。
- **代价**：Android 各 ROM 省电策略会杀后台调度，需引导用户加入电池优化白名单。
- **收益**：闹钟、后台任务、震动、角标等系统能力全部可用，且 UI 代码零分叉。
- **排期**：M5 才做闹钟；但 M1 就落地 `platform` 接口与能力探测，避免返工。

## ADR-008 · 一个学期 = 一张课表，每张课表一套独立作息

**状态**：已确认（M1 落地）

### 背景
用户要的"课表"不止一张：主修、辅修、考研班可能同时存在；新学期也必须另起一张，
不能把上学期的课删光重录。同时"作息时间"（第几节几点上课）在不同课表下并不相同 ——
有的院系 8:00 上课，有的 8:30。

早期实现里有两个隐患：
1. `bootstrap()` 只建一个学期，界面上没有任何入口能再建第二个；
2. 作息配方存在**全局** meta 键 `scheduleConfig` 上，于是改 A 课表的作息会让
   B 课表的设置页显示成 A 的参数，一旦保存就把 B 的作息覆盖掉。

### 决策
1. **界面上叫「课表」，数据层里就是 `Semester`**：一个学期对应一张课表。
2. **作息配方按课表分开存**，键为 `scheduleConfig:<semesterId>`；
   读取时回退到旧全局键，老数据无需迁移即可继续工作。
3. **任何时刻最多一张课表是"当前"**（`isActive`），由 `activateSemester()` 统一维护，
   界面不允许出现两张都亮。
4. **新建课表默认沿用当前课表的作息**，但生成的是独立副本；之后互不影响。
5. **删课表 = 连它的课程、场次、调课记录、作息配方一起删**；
   删的若正是当前课表，自动把剩下最新的一张设为当前；一张不剩时直接进"新建"。
6. **视图层必须用 `blocks.listBySemester(id)`，禁止用 `listCourses()`** ——
   后者返回所有课表的课，切课表时会串课。

### 理由
- 「一张课表一套作息」是**语义正确**的最小划分：作息属于学期的教学安排，不属于用户偏好。
- 键按学期分开是**向后兼容**的加法：旧库仍能读，新库结构清晰，无需写迁移脚本。
- 把"最多一张活跃"和"删完自动补位"收敛到数据层的一个函数里，
  界面就不可能绕过去制造出半死状态（用户卡在"一个学期都没有"的空界面上）。

### 后果
- **代价**：meta 里会有多条 `scheduleConfig:<id>`；删除课表时必须记得清理（已实现）。
- **代价**：`ScheduleSettings` 等组件需要 `semester.id` 才能读配置，签名变长。
- **收益**：多课表并存、切换、删除都不串数据；备份/恢复天然覆盖（meta 全量导出）。
- **验收**：`packages/data/src/semesters.test.ts` 用 18 个用例守住三条不变量
  （最多一张活跃 / 作息互不影响 / 删除后不会卡住）。

## ADR-009 · 调课的语义：`moved` 标在"原时间"上

**状态**：已确认（M1 修正）

### 背景
`Adjustment` 支持 `cancel`（停课）/ `move`（调课）/ `add`（补课）。
早期 `materializeAll()` 把 `move` 的 `status: 'moved'` 打在**新日期**那一条上，
原时间那一条保持 `normal` —— 结果是**同一次课在原时间与新时间各显示一遍**，
而且"下一节是什么课"会把已经调走的课算进去。

### 决策
1. **`moved` 描述"原时间上那一次"**：这里已经没课了，界面上置灰划线并标「已调走」。
2. **挪过去的那一次是 `normal`**，用新字段 `movedFrom` 记下原日期，界面标「调课 · 原定 X」。
3. **新增 `isOccurrenceActive(occ)`**：`status` 既不是 `cancelled` 也不是 `moved`。
   "下一节""正在进行中""今天几节课""冲突检测""顶部课次统计"一律用它，
   **不允许**再手写 `status !== 'cancelled'`。
4. **`Adjustment.id` 确定性**（`adj_<blockId>#<date>`），同一门课同一天只有一条记录；
   先停课后改调课是覆盖，不会留下两条互相矛盾的记录。
5. 撤销调课 = 删掉那条 `Adjustment`，场次重建后课程恢复原样。

### 理由
- 判断"这一次到底上不上"必须有**唯一**判据；散落的 `status !== 'cancelled'` 迟早漏一处。
- `movedFrom` 是**纯派生字段**：`Occurrence` 每次变更都整体重建、且不进备份，
  所以加字段零迁移成本（对比：改 `Block` 结构就是真迁移）。
- 两端都能找到同一条记录（`findAdjustmentForOccurrence` 同时匹配原日期与新日期），
  用户从调课后的新时间点进去也能"恢复原样"，不会出现"这头撤销了、那头还在"。

### 后果
- **代价**：`materializeAll` 的逻辑比之前多一层判断；`Occurrence` 多一个可选字段。
- **收益**：调课不再重复显示；停课/调课后的"下一节"提示正确；撤销入口两端可达。
- **验收**：`packages/core/src/{materialize,occurrences,adjustments}.test.ts` 与
  `packages/data/src/repos.test.ts` 均有用例守着（含"不会显示两遍"与"统计数据不虚高"）。

## ADR-011：计划与待办统一事项模型

日期：2026-10-07
状态：接受（指导约束，尚未全部实现）

**背景**：计划需要表达截止日、区间和重复规则，待办需要表达下一步行动；分成两套数据会导致重复录入和状态不一致。

**决定**：以一套可扩展事项模型作为唯一来源。计划、待办和今天页是不同视图；事项包含时间规则、状态、优先级及课程/项目关联等可选字段。先完成本地离线闭环，再增加提醒、同步和插件。

**结果**：用户只维护一次，完成或延期能同步到所有入口；模型需要迁移时保持旧数据可读。UI 可按模块开关隐藏入口，但不能删除底层数据。
